## 一、Git 进阶：让仓库在第 50 次实验后还能看

### 1.1 核心问题：一个人为什么还需要分支

因为你的工作有三种状态，混在一条线上一定出事：

| 状态 | 例子 | 要求 |
|---|---|---|
| 能出结果的稳定版 | 论文里那组数字 | 不能随便动 |
| 正在开发的版本 | 新加损失函数 | 可以半成品 |
| 单个功能实验 | 试 focal loss | 失败就删 |

**全放 main 的后果：** 你改到一半，导师让跑旧实验；你 stash 或手动注释，跑完改回来时漏了一行，旧结果再也复现不出来。

**不用分支不是不能干活，是干活的过程会污染已验证的结果。**

### 1.2 最小分支模型

| 分支 | 放什么 | 规则 |
|---|---|---|
| `main` | 能出论文数字的版本 | 只能通过 PR 合入，每次打 tag |
| `develop` | 已集成、未定稿 | 功能分支从这里切 |
| `feature/xxx` | 一个功能或一组实验 | 以天计，做完就删 |

```bash
git checkout develop && git pull
git checkout -b feature/focal-loss
git add loss.py train.py
git commit -m "feat: add focal loss with gamma configurable"
git push -u origin feature/focal-loss
```

**命名要能看出意图：** `feature/focal-loss` 好过 `test`；`fix/dice-empty-mask` 好过 `fix`；实验分支带日期，如 `exp/lr-sweep-0715`。

### 1.3 rebase vs merge

- `merge`：保留两条历史，生成合并提交，提交哈希不变
- `rebase`：把你的提交重新应用到目标分支后面，历史成直线，**哈希会变**

**本机实测（`git_demo` 仓库）：**

变基前：

```
* 393ce13 develop: update dev.txt
| * 294da97 feat: add focal loss
|/
* 2fdbe0f develop: add dev.txt
```

执行 `git rebase develop` 后：

```
* f2b1216 feat: add focal loss
* 393ce13 develop: update dev.txt
* 2fdbe0f develop: add dev.txt
```

`294da97` 变成 `f2b1216`。rebase 不是"移动"提交，是"重新生成"提交。

**决策表：**

| 场景 | 用哪个 | 原因 |
|---|---|---|
| 自己的 feature，未推送 | `rebase develop` | 历史干净，没有无意义合并提交 |
| 已推送但只有自己在用 | `rebase` + `push --force-with-lease` | 可以，但要提前说 |
| 已有人基于它开发 | `merge` | rebase 会让别人历史对不上 |
| feature 合回 develop | `merge --no-ff` | 保留"这是一个功能"的边界 |
| main 热修复 | `merge` | 稳定分支不改写历史 |

**铁律：不要 rebase 已经推送到共享分支的提交。**

```bash
git push --force              # 错误：覆盖别人提交且无警告
git push --force-with-lease   # 正确：远端有新提交时拒绝
```

**实测 merge 输出：**

```
$ git merge --no-ff feature/focal-loss -m "Merge branch 'feature/focal-loss' into develop"
Merge made by the 'ort' strategy.
 loss.py | 1 +
 1 file changed, 1 insertion(+)
```

`--no-ff` 强制生成合并提交；不加的话，develop 没有新提交时 Git 会快进，历史里看不出曾经有功能分支。

### 1.4 PR 流程与 Code Review

```bash
git checkout develop && git pull
git checkout -b feature/new-metric
git commit -m "feat: add dice metric"
git commit -m "test: add dice unit tests"
git fetch origin && git rebase origin/develop   # 推送前自己解决冲突
python -m pytest -q                              # 必须跑
git push -u origin feature/new-metric
```

**Review 看五条：**

| 检查项 | 看什么 | 为什么 |
|---|---|---|
| 正确性 | 边界、空张量、除零 | 脚本崩在半夜最亏 |
| 可复现 | 种子、路径、超参来源 | 换机器能不能跑 |
| 副作用 | 全局变量、覆盖文件 | 实验互相污染 |
| 测试 | 新函数有没有测试 | 以后敢不敢重构 |
| 可读性 | 函数名、魔法数字 | 三个月后的自己 |

**提交前缀：** `feat:` 新功能、`fix:` 修 bug、`exp:` 实验性改动、`docs:` 文档、`chore:` 杂事、`test:` 测试。

### 1.6 Git LFS

Git 保存每个版本的完整副本，二进制大文件会让仓库指数膨胀。

| 文件 | 大小 | 方案 |
|---|---|---|
| 模型权重 | 10 MB - 2 GB | Git LFS |
| 小型示例数据 | < 10 MB | 直接提交 |
| 完整数据集 | > 1 GB | DVC 或网盘 |
| 预训练权重 | 任意 | 下载脚本 + 校验和 |

**实测（git-lfs 3.7.1）：**

```
$ git lfs track "*.pt"
Tracking "*.pt"
$ cat .gitattributes
*.pt filter=lfs diff=lfs merge=lfs -text
```

`git lfs track` 只写规则，不会转换已提交文件；已提交的要用 `git lfs migrate import`，它会改写历史。

### 1.7 本节常见错误

| 错误 | 现象 | 正确做法 |
|---|---|---|
| main 上直接开发 | 稳定版被污染 | 从 develop 切 feature |
| rebase 共享分支 | 同事历史错乱 | 共享分支只用 merge |
| `push --force` | 覆盖别人提交 | `--force-with-lease` |
| 提交信息写 update | 历史无法阅读 | feat/fix/exp 前缀 |
| 提交 best.pt | 仓库无法 clone | .gitignore + LFS |
| .gitignore 对已跟踪文件无效 | 忽略不生效 | `git rm --cached 文件名` |
| 一个提交改 20 个文件 | 无法 review/回滚 | 一次提交一件事 |

## 二、实验管理：为什么手写笔记一定会崩

### 2.1 核心问题

第 1 次实验记得住，第 50 次呢？

```
第 1 次：lr=0.001, bs=32, val_acc=0.87   记在笔记本
第 10 次：试了 5 个 lr，画表格
第 25 次：笔记本丢了，改 Excel
第 40 次：Excel 有三个版本，不知道哪个最新
第 50 次：论文要写"我们做了网格搜索"，哪组最好只能猜
```

**不是记性问题，是工具问题。** 人脑不擅长管理 50 组多维参数。

| 能力 | 手写笔记 | 实验管理工具 |
|---|---|---|
| 记录超参 | 容易漏 | 自动，与运行时一致 |
| 记录每轮指标 | 只记最后 | 每 epoch/step 自动 |
| 对比多次实验 | 人眼看 | 勾选曲线叠加 |
| 找回当时的代码 | 靠记忆 | 关联 git commit |
| 共享给导师 | 截图 | 一个链接 |

### 2.2 TensorBoard / W&B / MLflow 对比

| 维度 | TensorBoard | W&B | MLflow |
|---|---|---|---|
| 安装 | `pip install tensorboard` | 装包 + 账号 | `pip install mlflow` |
| 联网 | 不需要 | 需要（可离线缓存） | 本地服务 |
| 学习成本 | 低 | 低 | 中 |
| 曲线对比 | 一般 | 强（筛选、平行坐标） | 中 |
| 超参搜索 | 无 | sweeps | 有 |
| 产物管理 | 无 | Artifacts | 有 |
| 团队协作 | 弱 | 强（云端） | 中（自建） |
| 适合 | 个人、离线 | 团队、论文对比 | 企业内网 |

**选择：主力 TensorBoard（本机已验证）；投实习前补 W&B（简历有分量）；MLflow 知道区别即可。** 不用 TensorBoard 的后果：每轮指标只留在终端滚动缓冲里，关掉窗口就没了。

**为什么必须至少用一个：** 面试官问"0.87 那组用了什么学习率"，答"我回去查一下"，这一句就结束了。

### 2.3 必须记录的四类信息

| 类别 | 内容 | 不记的后果 |
|---|---|---|
| 超参 | lr、batch、epochs、模型、损失、增强 | 无法复现，也无法解释差异 |
| 指标 | 每轮 train/val loss、AUC/Dice、lr | 看不出过拟合从哪轮开始 |
| 产物 | checkpoint、预测图、混淆矩阵、配置 | 不知道 best.pt 是哪次的 |
| 代码版本 | git commit、是否有未提交改动 | 代码改了结果没重跑 |

再加环境信息：Python、PyTorch、CUDA 版本。`torch.compile` 在不同版本行为不同，复现失败常是环境差异。

### 2.4 命名与目录规范

Hydra 按时间建目录，但目录名不携带信息，建议额外写 `meta.json`：

```python
import json
import platform
import subprocess
from pathlib import Path

import torch

def git_commit() -> str:
    """返回当前 commit，取不到返回 unknown。"""
    try:
        return subprocess.check_output(
            ["git", "rev-parse", "--short", "HEAD"], text=True
        ).strip()
    except Exception:
        return "unknown"

def dump_meta(run_dir: Path, cfg_dict: dict) -> None:
    """把环境、代码版本、配置写进运行目录。"""
    meta = {
        "git_commit": git_commit(),
        "python": platform.python_version(),
        "torch": torch.__version__,
        "cuda": torch.version.cuda,
        "gpu": torch.cuda.get_device_name(0) if torch.cuda.is_available() else "cpu",
        "config": cfg_dict,
    }
    (run_dir / "meta.json").write_text(
        json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8"
    )
```

运行目录（Hydra 生成）：

```
outputs/2026-11-05/14-19-37/
  .hydra/config.yaml      # 完整配置（含命令行覆盖）
  meta.json               # 环境 + git commit
  best.pt
  tb/pneumo_smallcnn/events.out.tfevents...
```

**面试说法：** 每次运行独立目录，存完整 config、git commit、环境版本、checkpoint。任何数字都能定位到唯一的代码+配置+数据组合。

### 2.9 本节常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 只记最后指标 | 看不出过拟合 | 每 epoch 都记 |

| 只看 accuracy | 类别不平衡时被骗 | 加 AUC、召回、混淆矩阵 |

## 三、配置管理：Hydra 与 `--multirun`

### 3.1 核心问题

超参写在代码里有三种死法：

| 死法 | 场景 | 后果 |
|---|---|---|
| 改参数要改代码 | 试 10 个 lr | 10 次修改，容易改错漏 |
| 无法批量跑 | 3×3 网格 | 手写 9 条命令或丑陋循环 |
| 配置丢失 | 两周后回看 | 只记得"好像用过 0.0005" |

**不用 Hydra 的后果：** 配置散落在代码、命令行和记忆三处，迟早对不上。

### 3.5 三个真实踩过的坑

**坑 1：覆盖不存在的键**

```
$ python train.py train.batch_size=64
Could not override 'train.batch_size'.
Key 'batch_size' is not in struct
    full_key: train.batch_size
```

`batch_size` 在 `data` 下面，不在 `train` 下面。Hydra 报错已经告诉你完整键名。

**坑 2：multirun 日志全写进同一目录**

第一版用了 `run_dir = Path(os.getcwd())`，四个 job 的 TensorBoard 全写到 `code/runs/pneumo_smallcnn`，曲线互相覆盖，等于白跑。

原因：Hydra 1.2 后 `hydra.job.chdir` 默认 `False`，工作目录不自动切。

```python
from hydra.core.hydra_config import HydraConfig
run_dir = Path(HydraConfig.get().runtime.output_dir)
```

**这个坑正好是本章要解决的问题：实验互相污染。**

**坑 3：改 YAML 忘了代码里写死**

YAML 里 `epochs: 5`，代码里 `for epoch in range(5)`，改成 10 还是只跑 5 轮。规则：代码里不允许出现超参数字。

### 3.6 本节常见错误

| 错误 | 现象 | 正确做法 |
|---|---|---|
| 超参写死 | 配置与实际不符 | 全部从 cfg 读 |
| `os.getcwd()` 当输出目录 | multirun 混一起 | 用 Hydra runtime 目录 |
| 覆盖错误层级 | `Key not in struct` | 先 `print(cfg)` |
| 忘写 `version_base=None` | 警告、目录不一致 | 显式写 |
| multirun 开太多 job | 显存爆 | 限制并发 |
| 删了 `.hydra/` | 无法复现 | 保留运行目录 |

## 四、数据版本管理：DVC

### 4.1 核心问题

| 问题 | Git 的表现 |
|---|---|
| 数据 5 GB | 仓库爆炸，clone 几小时 |
| 每版改一点 | 每版存完整副本 |
| 数据在网盘 | 代码和数据版本对不上 |
| 想回到"v1 数据 + v2 代码" | 做不到 |

**不用 DVC 会怎样：** `liver_v1/`、`liver_v2/`、`liver_v2_fixed/`、`liver_v2_fixed_最终/`，三个月后不知道论文的 0.94 用的哪个。

### 4.2 原理

DVC 不把数据存进 Git：

1. 算数据哈希（md5）
2. 复制进 `.dvc/cache/`（可配置到网盘/S3）
3. 生成很小的 `.dvc` 文件记录哈希和路径

Git 只提交 `.dvc` 文件，数据与代码就这样绑定。

```
data/raw/                 <- 真数据，被 .gitignore 忽略
data/raw.dvc              <- 几行文本，进 Git
.dvc/cache/files/md5/...  <- 内容寻址缓存
```

### 4.3 实测流程

```bash
dvc init
git add .dvc .dvcignore
git commit -m "chore: init dvc"

dvc add data/raw                 # 把数据交给 DVC
git add data/raw.dvc data/.gitignore
git commit -m "data: add raw dataset v1"
```

实测 `data/raw.dvc`：

```yaml

  size: 49536
  nfiles: 3
  hash: md5
  path: raw
```

`data/.gitignore` 自动生成，内容是 `/raw`，所以数据不进 Git。

版本恢复实测：

```

# 改坏一个文件后
```

### 4.4 数据和代码怎么绑定

同一个 commit 里同时包含代码和 `.dvc` 改动：


### 4.6 本节常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 数据直接 `git add` | 仓库爆炸 | `dvc add` |
| 只提交 `.dvc` 不提交代码 | 版本错位 | 同一个 commit |
| 换机器只 clone 代码 | checkout 找不到缓存 | `dvc pull`（配 remote） |

## 五、代码质量：类型注解、docstring、pytest

### 5.1 核心问题

三个具体场景：

- 三个月后看 `def f(x, y, z)`，不知道 x 是 tensor 还是路径
- 同事给 `compute_dice` 传了 logits 而不是 0/1 掩码，结果 0.99，没人发现
- 重构预处理改坏形状，训练 6 小时后才发现 loss 不降

**类型注解解决第一个，docstring 解决第二个，pytest 解决第三个。不写测试的后果：重构一次就可能悄悄改坏预处理，训练跑了 6 小时才发现 loss 不降。**

### 5.2 类型注解

```python
from __future__ import annotations

import torch

def compute_dice(
    pred: torch.Tensor,
    target: torch.Tensor,
    smooth: float = 1e-6,
) -> float:
    ...
```

| 位置 | 写法 | 例子 |
|---|---|---|
| 参数 | 类型 | `images: torch.Tensor` |
| 返回 | 类型 | `-> float` |
| 可为空 | `X | None` | `ckpt: str | None = None` |
| 容器 | 元素类型 | `list[int]`、`dict[str, float]` |

`from __future__ import annotations` 让 Python 3.11 也能用新写法，写在文件第一行。

### 5.3 docstring（Google 风格）

```python
def dice_score(
    pred: torch.Tensor, target: torch.Tensor, smooth: float = 1e-6
) -> float:
    """计算二值掩码的 Dice 系数（按 batch 求平均）。

    Args:
        pred: 预测掩码，形状 (B, 1, H, W)，值域 0-1
        target: 真实掩码，形状同 pred
        smooth: 平滑项，防止分母为 0

    Returns:
        batch 内平均 Dice，范围 [0, 1]

    Raises:
        ValueError: 形状不一致或张量为空
    """
```

必须写清：形状（医学影像最常错维度顺序）、值域（0-1 还是 0-255、logits 还是概率）、异常。

### 5.4 pytest 测什么

| 类型 | 测什么 | 例子 |
|---|---|---|
| 数据预处理 | 形状、dtype、值域 | (28,28) uint8 → (1,28,28) float32，[0,1] |
| 指标计算 | 手算例子验证数值 | 完全重叠 Dice=1，不重叠 Dice=0 |
| 模型前向 | 输入输出维度、有限值 | (8,1,28,28) → (8,2) |

**不测：** PyTorch 官方算子、需要长训练的端到端流程、不固定的随机结果。

### 5.5 三个必写的测试（实测通过）

```python
import pytest
import torch

from metrics import dice_score

def test_dice_perfect() -> None:
    """预测和真值完全一样，Dice 必须是 1。"""
    pred = torch.ones(1, 1, 4, 4)
    assert dice_score(pred, pred) == pytest.approx(1.0, abs=1e-4)

def test_dice_no_overlap() -> None:
    """完全不相交，Dice 必须是 0（有 smooth 时接近 0）。"""
    pred = torch.zeros(1, 1, 4, 4)
    pred[..., :2, :] = 1
    target = torch.zeros(1, 1, 4, 4)
    target[..., 2:, :] = 1
    assert dice_score(pred, target) < 1e-3

def test_dice_known_value() -> None:
    """手算：各 4 个 1、重叠 2 个，Dice = 2*2/(4+4) = 0.5。"""
    pred = torch.tensor([1, 1, 1, 1, 0, 0, 0, 0], dtype=torch.float32).view(1, 1, 2, 4)
    target = torch.tensor([1, 1, 0, 0, 1, 1, 0, 0], dtype=torch.float32).view(1, 1, 2, 4)
    assert dice_score(pred, target) == pytest.approx(0.5, abs=1e-4)
```

## 六、模型导出与部署

### 6.1 核心问题

`model.pt` 变成别人能调用的服务，中间有三道坎：

1. **格式**：PyTorch checkpoint 不是通用格式
2. **接口**：别人不能 import 你的训练脚本
3. **环境**：别人机器上没有 CUDA 2.9.1

### 6.2 四种格式对比（大小为本机实测）

| 格式 | 保存什么 | 加载需要 | 优点 | 缺点 | 实测大小 |
|---|---|---|---|---|---|
| `state_dict` | 只有参数 | 模型类 + 代码 | 最稳、最小、可控 | 必须带源码 | 101.0 KB |
| 完整模型 | 参数 + 结构 | 模型类 | 省事 | pickle 不安全、重构易坏 | 104.8 KB |
| TorchScript | 参数 + 图 | 只要 torch | 可脱离源码 | 动态控制流受限 | 119.8 KB |
| ONNX | 图 + 参数 | onnxruntime | 跨语言、CPU 快 | 动态 shape 要声明 | 93.6 KB |

模型参数量：23,650。

**为什么推荐 state_dict：** 只存参数不存代码；不受 pickle 反序列化漏洞影响；文件最小；`load_state_dict` 缺键多键会报错，自带校验。

**不用 state_dict 的后果：** 半年后重构模型类、改了构造参数，旧文件直接加载失败，报错还很难懂。

### 6.3 ONNX 导出 + 一致性验证（实测）

**为什么用 ONNX：** 训练用 PyTorch，部署用 onnxruntime（C++ 实现，CPU 通常更快）；医院内网服务器不一定能装 PyTorch+CUDA；同一模型可给 Python/C++/C#/Java 调用。

```python
from pathlib import Path

import numpy as np
import onnx
import onnxruntime as ort
import torch

from model import SmallCNN

model = SmallCNN(1, 2)
model.load_state_dict(torch.load("outputs/2026-11-05/14-19-37/best.pt", map_location="cpu"))
model.eval()

dummy = torch.randn(1, 1, 28, 28)
torch.onnx.export(
    model,
    dummy,
    "best.onnx",
    input_names=["input"],
    output_names=["logits"],
    dynamic_axes={"input": {0: "batch"}, "logits": {0: "batch"}},
    opset_version=17,
    dynamo=False,
)

onnx_model = onnx.load("best.onnx")
onnx.checker.check_model(onnx_model)
print(f"ONNX 文件大小: {Path('best.onnx').stat().st_size / 1024:.1f} KB")
```

**`dynamic_axes` 是最容易漏的一行。** 不写只能接受 batch=1，服务端一次来 8 张就报错。

实测输出：


### 6.4 FastAPI 服务（实测）

**为什么用 FastAPI：** 自动生成 `/docs`，别人不看代码就能调；类型校验免费；异步支持适合读图和推理。

```python
import io
import os
from contextlib import asynccontextmanager

import numpy as np
import onnxruntime as ort
import uvicorn
from fastapi import FastAPI, File, HTTPException, UploadFile
from PIL import Image

MODEL_PATH = os.getenv("MODEL_PATH", "best.onnx")
CLASS_NAMES = ["normal", "pneumonia"]
_session: ort.InferenceSession | None = None


@asynccontextmanager
async def lifespan(app: FastAPI):
    """启动时加载模型，关闭时释放。只加载一次。"""
    global _session
    _session = ort.InferenceSession(MODEL_PATH, providers=["CPUExecutionProvider"])
    yield
    _session = None


app = FastAPI(title="PneumoniaMNIST 推理服务", version="1.0", lifespan=lifespan)


def preprocess(raw: bytes) -> np.ndarray:
    """PNG 字节 -> (1,1,28,28) float32，规则必须和训练一致。"""
    try:
        img = Image.open(io.BytesIO(raw)).convert("L").resize((28, 28))
    except Exception as exc:
        raise HTTPException(status_code=400, detail=f"无法解析图片: {exc}") from exc
    x = np.asarray(img, dtype=np.float32) / 255.0
    return x[None, None, :, :]


def softmax(logits: np.ndarray) -> np.ndarray:
    z = logits - logits.max(axis=1, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=1, keepdims=True)


@app.get("/health")
def health() -> dict:
    return {"status": "ok", "model": MODEL_PATH}


@app.post("/predict")
async def predict(file: UploadFile = File(...)) -> dict:
    if _session is None:
        raise HTTPException(status_code=503, detail="模型未加载")
    if file.content_type not in {"image/png", "image/jpeg"}:
        raise HTTPException(status_code=415, detail="只支持 PNG/JPEG")

    x = preprocess(await file.read())
    logits = _session.run(None, {"input": x})[0]
    probs = softmax(logits)[0]
    idx = int(probs.argmax())
    return {
        "label": CLASS_NAMES[idx],
        "confidence": round(float(probs[idx]), 4),
        "probabilities": {n: round(float(p), 4) for n, p in zip(CLASS_NAMES, probs)},
    }
```

```bash

```

```
$ curl -s -X POST -F "file=@test_sample.png" http://127.0.0.1:8011/predict
```

```bash
python -m uvicorn app:app --host 0.0.0.0 --port 8000
```

区别：venv 不隔离系统库和 CUDA，换机器仍可能出问题；Docker 连操作系统层一起打包。不用 Docker 的后果就是"在我电脑上能跑"，换台机器重装 CUDA 和驱动能折腾一天。**面试时说清这个区别，比假装会用 Docker 强。**

### 6.6 本节常见错误

| 错误 | 现象 | 正确做法 |
|---|---|---|
| 导出忘了 eval | 输出误差大 | 先 `model.eval()` |
| 不写 dynamic_axes | 只能 batch=1 | 显式声明 batch 维 |
| 导出后不验证 | 线上全错才发现 | 逐 batch 比对误差 |
| 用完整模型交付 | 换环境加载失败 | state_dict + 模型代码 |
| 每请求加载模型 | 延迟几百 ms | lifespan 加载一次 |
| 预处理和训练不一致 | 线上指标暴跌 | 写成函数并测试 |
| Docker `COPY . .` | 镜像含大量垃圾 | .dockerignore + 精确 COPY |
| 容器用 root | 安全风险 | 建普通用户 |

## 七、推理优化：每一项的真实加速比

### 7.1 核心问题

网上常说"no_grad 快 3 倍""半精度快 2 倍"。**这些数字有前提，不测就信会误导你。**

以下全部本机实测：RTX 5060 Laptop 8GB，ResNet18，224x224，batch=1，warmup 5 次后 30 次中位数。

### 7.2 实测总表

| 优化 | 设置 | 优化前 | 优化后 | 加速比 |
|---|---|---|---|---|
| `torch.no_grad()` | bs=1，fp32 | 9.37 ms | 8.94 ms | 1.05x |
| `model.half()` | bs=1 | 8.94 ms | 7.53 ms | 1.19x |
| autocast | bs=1 | 8.94 ms | 6.59 ms | 1.36x |
| 批处理 | bs=1 → bs=8 | 104.9 张/秒 | 851.4 张/秒 | 8.1x |
| channels_last | bs=32 | 44.69 ms | 42.20 ms | 1.06x |
| 梯度检查点（3D） | 训练显存 | 2965.9 MB | 1813.9 MB | 省 38.8% |

**结论：no_grad 主要省显存不是省时间；半精度只有 1.2-1.4x；批处理是唯一数量级优化；检查点拿时间换显存。**

### 7.3 `torch.no_grad()`：省的是显存

推理不需要梯度，不建计算图、不保存中间激活。

```
no_grad=8.94 ms   with_grad=9.37 ms   加速 1.05x
```

bs=1 时 GPU 大部分时间在等 kernel 启动和内存拷贝，保存激活的占比很小。但显存差距大（bs=32）：

| 模式 | 峰值显存 |
|---|---|
| `no_grad` | 257.1 MB |
| 有梯度 | 780.6 MB |

**3.04 倍。** 所以服务端必须写 no_grad（或用 ONNX，本来就没有梯度）。

### 7.4 半精度

```python
# A：模型和输入都转 half
model_h = model.half()
x_h = x.half()
with torch.no_grad():
    out = model_h(x_h)

# B：autocast（推荐）
with torch.no_grad(), torch.autocast("cuda", dtype=torch.float16):
    out = model(x)
```

| 方式 | 延迟 | 加速 |
|---|---|---|
| fp32 | 8.94 ms | 1.00x |
| `model.half()` | 7.53 ms | 1.19x |
| autocast | 6.59 ms | 1.36x |

注意：CPU 上 fp16 通常更慢；softmax/LayerNorm 可能溢出，autocast 比手动 half 安全；精度影响要和 fp32 比对，分类结果不能变。

### 7.5 批处理

| batch | 每批耗时 | 吞吐 |
|---|---|---|
| 1 | 9.54 ms | 104.9 张/秒 |
| 8 | 9.40 ms | 851.4 张/秒 |
| 32 | 37.64 ms | 850.2 张/秒 |
| 128 | 183.10 ms | 699.1 张/秒 |

bs=1 到 bs=8 每批耗时几乎不变，吞吐 8 倍；bs=32 算力吃满；bs=128 反而下降。**找到吞吐平台期，不要盲目加大。**

服务端请求级 batching 能拉高并发吞吐，但增加单请求延迟；医疗场景单张、低并发，收益有限。

### 7.6 channels_last

PyTorch 默认 NCHW，GPU 卷积底层偏爱 NHWC。

```python
model = model.to(memory_format=torch.channels_last)
x = x.to(memory_format=torch.channels_last)
```

实测 bs=32：44.69 → 42.20 ms，1.06x。免费的小优化，别期待奇迹；大分辨率分割模型收益更明显。

### 7.7 梯度检查点

前向不保存中间激活，反向重算。

| 实验 | 普通 | 检查点 | 代价 |
|---|---|---|---|
| ResNet18，bs=32 | 191.6 ms，1070.2 MB | 225.7 ms，1025.0 MB | 慢 1.18x，只省 4.2% |
| 3D CNN，输入 (4,1,64,64,64) | 1281.8 ms，2965.9 MB | 1723.6 ms，1813.9 MB | 慢 1.34x，省 38.8% |

ResNet18 激活相对模型本身小，且 conv1 没包进检查点，所以几乎不省。**3D 医学影像是主场：** 激活占显存大头时，34% 的时间换 39% 显存很划算，因为不检查点根本跑不起来。

```python
from torch.utils.checkpoint import checkpoint_sequential

h = model.stem(x)
h = checkpoint_sequential(model.stages, 4, h, use_reentrant=False)
out = model.head(h)
```

`use_reentrant=False` 要显式写，不写有警告且新版本默认行为会变。

### 7.8 优化决策表

| 瓶颈 | 先做什么 | 预期收益 |
|---|---|---|
| 服务端显存不够 | `no_grad` + ONNX | 显存降 3 倍 |
| CPU 服务太慢 | 导出 ONNX | 实测 3.22x（小模型） |
| GPU 吞吐低 | 加 batch 到平台期 | 实测 8.1x |
| 单张延迟高 | 半精度 / autocast | 1.2-1.4x |
| 训练 OOM | 梯度检查点 / 减 batch | 3D 省 38.8% |
| 大模型推理慢 | TensorRT / ONNX+fp16 | 未实测，不写数字 |

**先测量，再优化。** 不测就上半精度，可能发现瓶颈不在计算。

### 7.9 本节常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 推理忘 no_grad | 显存 3 倍，可能 OOM | 推理统一加 |
| CPU 上用 fp16 | 更慢 | CPU 用 fp32 + ONNX |
| 手动 half 忘转输入 | dtype 不匹配 | autocast 更安全 |
| batch 越大越好 | 过平台期反而慢 | 测吞吐曲线找拐点 |
| 拿训练脚本测推理 | 结果含反向 | 单独写 benchmark |
| 只测一次 | 预热影响巨大 | warmup 5 次取中位数 |
| 不同步 CUDA | 计时偏小 | 计时前后 synchronize |

## 十、自测题（8 道）

### 题 1：rebase 和 merge 的区别？什么时候用哪个？

<details><summary>看答案</summary>

merge 保留两条历史线、生成合并提交、哈希不变；rebase 把提交重新应用到目标分支后面，历史成直线，但哈希会变。

自己的、未推送的 feature 用 rebase；已推送的共享分支、合回 develop/main 用 merge --no-ff。铁律：不要 rebase 共享分支上已推送的提交；强推用 `--force-with-lease`。

</details>

### 题 2：为什么实验管理不能用 Excel？

<details><summary>看答案</summary>

Excel 能记数字，但记不了完整超参（容易漏）、每轮指标（只记最后一行）、产物与代码版本的对应、可筛选的对比视图。而且靠手填，和实际运行配置会不一致。

第 50 次实验后会有多个版本，不知道哪个最新，也无法回答"batch_size 影响多大"。

</details>

### 题 3：`no_grad()` 省了什么？为什么 bs=1 几乎不提速？

<details><summary>看答案</summary>

省计算图和中间激活。反向需要这些激活，推理不需要。

bs=1 只快 1.05x，因为瓶颈在 kernel 启动和数据搬运。但显存差距大：bs=32 时 257.1 MB vs 780.6 MB，约 3 倍。所以它的主要价值是显存。

</details>

### 题 4：state_dict、完整模型、ONNX、TorchScript 怎么选？

<details><summary>看答案</summary>

续训、自己用：state_dict，最稳最小，加载能发现结构不匹配。

不跨语言但要脱离源码：TorchScript。

给 C++/Java/内网无 PyTorch：ONNX + onnxruntime。

完整模型不推荐：依赖 pickle，重构后易加载失败，有反序列化风险。

本机大小：101.0 / 104.8 / 119.8 / 93.6 KB。

</details>

### 题 5：ONNX 导出后怎么验证？

<details><summary>看答案</summary>

1. `onnx.checker.check_model` 检查图结构
2. 打印 input/output shape，确认 dynamic batch 是 dim_param 而不是固定数字
3. 同输入分别送 PyTorch 和 ORT，算最大绝对误差，确认 argmax 一致

本机 max_abs_err：3.815e-06（bs=1）、2.289e-05（bs=8）、1.526e-05（bs=32）。误差到 1e-2 通常是忘了 `model.eval()`，BatchNorm 用了训练模式。

</details>

### 题 6：DVC 和 Git 的分工？

<details><summary>看答案</summary>

Git 管代码和文本；DVC 管大数据和模型，数据放 `.dvc/cache` 或远端，Git 只提交记录哈希的 `.dvc` 文件。

两者靠同一个 commit 绑定：代码改动和 `.dvc` 一起提交，之后 `git checkout` + `dvc checkout` 同时恢复代码和数据。

不用的话，数据目录会出现 v1/v2/最终版，无法确定论文数字对应哪份数据。

</details>

### 题 7：单元测试测什么？不测什么？

<details><summary>看答案</summary>

测：预处理的形状/dtype/值域、指标的数值（手算例子）、模型前向维度、异常路径（形状不匹配要报错）。

不测：PyTorch 官方算子、长训练端到端流程、不固定的随机结果。

本机 7 个测试首次 8.53 秒、缓存后 2.55 秒，时间主要花在 import torch。

</details>

### 题 8：回答「你怎么管理实验」要包含哪几个要素？

<details><summary>看答案</summary>

四要素：

1. 工具：Hydra 管配置、TensorBoard/W&B 记指标、DVC 管数据、Git 管代码
2. 流程：每次运行独立目录，自动存 config、git commit、环境版本、checkpoint
3. 数字：能说出关键轮次和指标，如"第 4 轮 0.9466 最佳，第 5 轮过拟合"
4. 判断：能解释为什么选这个模型、为什么停在第 4 轮

只答"用 Excel 记录"是学生气；只列工具名却说不出数字，是背的。

</details>
