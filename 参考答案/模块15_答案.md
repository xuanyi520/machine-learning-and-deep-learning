### 练习 1（分支模型）

**参考代码**
```bash
# 在一个空目录里执行（本次实测用的是一次性演练仓库，未留在项目里）
git init -b main
git add . && git commit -m "init: train stub"

git checkout -b develop
git checkout -b feature/tensorboard-logging
# ……在 feature 分支上加 logging_util.py 并改 train.py……
git add . && git commit -m "feat: add tensorboard logging util"

# develop 上前进了另一个提交，模拟并行开发
git checkout develop
git add README.md && git commit -m "docs: add readme on develop"

# 把 feature rebase 到 develop 最新，再合回 develop
git checkout feature/tensorboard-logging
git rebase develop
git checkout develop
git merge --no-ff feature/tensorboard-logging -m "merge: tensorboard logging"
git tag v0.1

git log --graph --oneline --all
git tag
```

**实测输出**
```
*   2830cd4 merge: tensorboard logging
|\
| * 770a3a0 feat: add tensorboard logging util
|/
* 54da972 docs: add readme on develop
* 88c086e init: train stub

v0.1

$ python train.py
v1: tensorboard logging
```

**为什么合回用 merge 而不是 rebase**：`rebase` 会重写 feature 分支的提交哈希，把一个已经存在的分支历史"搬"到 develop 末尾；合回 develop 是一个**公共动作**，应该留下"这里合并过一条分支"的记录，所以用 `merge --no-ff` 强制生成合并提交。规则可以记成：**自己的、未推送的 feature 用 rebase 整理；合回共享分支用 merge --no-ff。** 如果对已推送的 develop 做 rebase，所有人的本地历史都会失效。

**判分要点**
- `git log --graph --oneline --all` 能看到两条线和一个合并点（`|\` 和 `|/`）。
- `git tag` 输出 `v0.1`，且 tag 打在合并后的提交上。
- 合并后 `python train.py` 能跑，说明没有把 feature 的改动弄丢。
- 能说清 rebase 改哈希、merge 保留历史；能说出"不要 rebase 共享分支"这条铁律。

**常见错误**
- 在 develop 上直接 `git merge feature` 但没加 `--no-ff`，快进合并后图上看不到分支。
- rebase 方向搞反（在 develop 上 rebase feature），把公共分支历史改了。
- tag 打在 feature 分支的旧提交上，而不是合并后的 develop。
- 合并冲突时用 `--ours/--theirs` 一把梭，丢掉了 feature 的改动。
- 用 `git push --force` 推共享分支，没有用 `--force-with-lease`。

```python
from omegaconf import OmegaConf
from tensorboard.backend.event_processing.event_accumulator import EventAccumulator
import glob

for d in sorted(glob.glob("multirun/2026-11-05/15-51-01/[0-9]*")):
```

**判分要点**
- `multirun/日期/时间/0..5` 六个独立目录，每个有自己的 `.hydra/config.yaml` 和 `tb/`。
- 结果表 6 行，每行有 lr、bs、best_acc，且 best_acc 注明是第几轮。
- 指出影响更大的超参时，必须给出计算方式（按 lr/bs 求均值或看极差），不能凭感觉。
- 能指出单种子、5 轮的局限，以及可能的交互作用。
- 复现命令只改必要参数，不写一长串默认值。

**常见错误**
- 用 `--multirun` 但没设 `hydra.sweeper`，参数只跑了第一组。
- 所有 job 写同一个 TensorBoard 目录，曲线重叠，读不出单组结果。
- 只报最后一轮的 acc，不报 best，超参比较被训练轮数干扰。
- 把 0.9695 当成"这个组合一定最好"，忽略种子方差。
- 复现命令写成 `python train.py --multirun ...`，跑出 6 组而不是 1 组。

### 练习 4（DVC 版本回滚）

**参考代码**
```bash
git init -b main
dvc init
python -c "import numpy as np, os; os.makedirs('data/raw'); [np.save(f'data/raw/vol{i}.npy', np.random.default_rng(i).normal(size=(32,32)).astype('float32')) for i in range(3)]"
```


三个 `.npy` 对应三个 blob，`.dir` 文件是目录清单（记录文件名 → md5 的映射）。

**`.dvc/cache` 存什么**：按内容寻址的 blob。文件名的前两位是目录，后 38 位是 md5；内容相同的文件只存一份，所以改一个文件只会新增一个 blob，不会复制整个目录。

**`dvc checkout` 和 `git checkout` 的分工**：

| 命令 | 管什么 | 恢复的是 |
|---|---|---|
| `git checkout` | 代码、`.dvc` 指针文件 | 切换 `.dvc` 里记录的 md5（但不碰真实数据） |
| `dvc checkout` | 真实数据 | 按当前 `.dvc` 的 md5 从 cache 还原文件 |

所以回滚数据版本的完整动作是：`git checkout <旧commit> -- data/raw.dvc`（或切分支）→ `dvc checkout`。只做前者，数据还是新的。

**判分要点**
- `data/raw.dvc` 里有 `md5`、`size`、`nfiles: 3`。
- `git status` 看不到 `data/raw/*.npy`，只能看到 `.dvc` 和 `.gitignore`。
- 能解释 cache 是按内容寻址，相同内容去重。
- 能说清 `git checkout` 改指针、`dvc checkout` 改数据，两步缺一不可。
- 改文件后 `dvc status` 显示 `modified`，`checkout --force` 后变干净。

**常见错误**
- 只 `git add data/raw`，大文件直接进了 git 历史。
- 改了数据但忘了 `dvc add`，`.dvc` 里的 md5 还是旧的。
- 只 `git checkout` 不 `dvc checkout`，以为数据回滚了。
- 把 `.dvc/cache` 加进 `.gitignore` 又删了本地缓存，数据再也取不回。
- 用 `dvc add` 之后又手动改文件名，目录清单对不上。

### 练习 5（补指标测试）

**参考代码**
```python
import pytest
import torch
from metrics import accuracy

def test_accuracy_all_correct() -> None:
    logits = torch.tensor([[2.0, 0.0], [0.0, 2.0]])
    labels = torch.tensor([0, 1])
    assert accuracy(logits, labels) == pytest.approx(1.0)

def test_accuracy_all_wrong() -> None:
    logits = torch.tensor([[2.0, 0.0], [0.0, 2.0]])
    labels = torch.tensor([1, 0])
    assert accuracy(logits, labels) == pytest.approx(0.0)

def test_accuracy_imbalanced_099_is_misleading() -> None:
    # 99 负 1 正，全预测为负 -> 0.99。这个数字只说明"多数类猜对了"，
    # 正类召回为 0；在筛查任务里等于什么都没查出来，不能用 accuracy 评价。
    logits = torch.zeros(100, 2)
    logits[:, 0] = 5.0
    labels = torch.zeros(100, dtype=torch.long)
    labels[0] = 1
    assert accuracy(logits, labels) == pytest.approx(0.99)
```

**为什么 0.99 不能说明模型好**：数据里 99 个负类、1 个正类，模型把所有样本判成负类，accuracy = 99/100 = 0.99，但正类召回 = 0/1 = 0。在筛查任务里，这意味着一个病人都没查出来。**accuracy 对类别不平衡不敏感，必须同时看敏感度、特异度、PPV/NPV、AUC。** 这也是为什么第三个测试要写成"断言 0.99"，而不是"断言模型好"——测试锁定的是函数的数值行为，不是模型质量。

**判分要点**
- 三个测试都通过，且没有改 `metrics.py` 的实现。
- 第一个 1.0、第二个 0.0、第三个 0.99，数值是手算的，不是跑出来再填。
- 第三个测试后的注释说清"多数类基线"和"正类召回为 0"。
- 测试只依赖 `metrics.py`，不 import Hydra/TensorBoard。
- 边界值用 `pytest.approx`，不用 `==` 比浮点。

**常见错误**
- 为了让测试过而改 `accuracy` 实现（比如加阈值），测试就失去意义。
- 第三个测试写成 `assert accuracy(...) > 0.9`，没有锁定精确值。
- 用随机 logits 做测试，结果不可复现。
- 测试里 import 整个 `train.py`，把 Hydra 的副作用带进来。
- 只测正常路径，不测空张量/形状不匹配。

### 练习 6（ONNX 导出验证）

**参考代码**
```python
import time, statistics
from pathlib import Path
import numpy as np
import onnx, onnxruntime as ort, torch
from model import SmallCNN

ckpt = sorted(Path("outputs").rglob("best.pt"), key=lambda p: p.stat().st_mtime)[-1]
model = SmallCNN(1, 2)
model.load_state_dict(torch.load(ckpt, map_location="cpu"))
model.eval()

torch.onnx.export(
    model, torch.randn(1, 1, 28, 28), "best.onnx",
    input_names=["input"], output_names=["logits"],
    dynamic_axes={"input": {0: "batch"}, "logits": {0: "batch"}},
    opset_version=17, dynamo=False,
)
m = onnx.load("best.onnx")
onnx.checker.check_model(m)
print([d.dim_param or d.dim_value for d in m.graph.input[0].type.tensor_type.shape.dim])

sess = ort.InferenceSession("best.onnx", providers=["CPUExecutionProvider"])
for bs in (1, 16, 64):
    x = torch.randn(bs, 1, 28, 28)
    with torch.no_grad():
        a = model(x).numpy()
    b = sess.run(None, {"input": x.numpy()})[0]
    print(bs, np.abs(a - b).max())

x = torch.randn(1, 1, 28, 28); xn = x.numpy()
for _ in range(10):
    with torch.no_grad(): model(x)
    sess.run(None, {"input": xn})
def bench(fn, n=200):
    ts = []
    for _ in range(n):
        t0 = time.perf_counter(); fn(); ts.append((time.perf_counter() - t0) * 1000)
    return statistics.median(ts), np.percentile(ts, 95)
with torch.no_grad():
    tp = bench(lambda: model(x))
to = bench(lambda: sess.run(None, {"input": xn}))
print(f"PyTorch {tp[0]:.3f} ms  ORT {to[0]:.3f} ms  加速 {tp[0]/to[0]:.2f}x")
```

**实测输出**
```

checker OK, size 93.6 KB
input dims: ['batch', 1, 28, 28]

=== 数值一致性 ===
batch=  1  max_abs=7.629e-06  max_rel=1.595e-07
batch= 16  max_abs=2.289e-05  max_rel=3.674e-07
batch= 64  max_abs=1.526e-05  max_rel=4.598e-07

=== CPU 延迟（batch=1，warmup 10，计时 200 次） ===
PyTorch    median 0.468 ms  p95 2.425 ms
ONNXRuntime median 0.104 ms  p95 0.129 ms  加速 4.49x

=== 吞吐随 batch ===
bs=  1    0.117 ms/批      8553 张/秒
bs=  8    0.138 ms/批     57919 张/秒
bs= 32    0.478 ms/批     66976 张/秒
bs=128    1.201 ms/批    106607 张/秒
```

**batch 越大误差为何可能略大**：ONNX Runtime 和 PyTorch 的卷积/矩阵乘实现不同，浮点累加顺序不同。batch 增大后，每层要处理的元素变多，误差在更多元素上累积；`max_abs` 取的是整个张量的最大绝对差，元素越多，碰到较大误差值的概率越高。但**相对误差始终在 1e-7 量级**，说明不是算子错误，只是浮点非结合性。判据应该同时看 `max_abs` 和 `max_rel`，只看绝对误差会被输出尺度误导。

**判分要点**
- `onnx.checker.check_model` 必须通过。
- 三个 batch 的 `max_abs_err < 1e-4`；本机最大 2.289e-05。
- 延迟报告要写清 warmup 次数、计时次数、取中位数还是均值；本机是 warmup 10、200 次、中位数。
- 加速比要写明比较对象（PyTorch CPU vs ORT CPU），不能拿 ORT CPU 和 PyTorch GPU 比。
- 能解释误差来源是浮点累加顺序，不是模型导出错。

**常见错误**
- 导出时没设 `dynamic_axes`，batch=16 直接报 shape mismatch。
- 只验证 batch=1，等于没验证动态轴。
- 用 `torch.randn` 但模型在 train 模式，BatchNorm 用 batch 统计，ONNX 和 PyTorch 对不上。
- 延迟测试不做 warmup，第一次包含图优化/内存分配，数字偏大。
- 报告"加速 4.49x"却不说是 CPU 上的对比，读者以为是 GPU。

```
中位数 = (0.002206 + 0.002275) / 2 = 0.00224 s ≈ 2.24 ms
```

**为什么要用 lifespan 加载模型**：`lifespan` 在服务启动时执行一次、关闭时执行一次。模型加载（读 ONNX、初始化 session）是百毫秒级操作，如果放在 `predict` 里，每个请求都要付一次；放在 lifespan 里，所有请求共享同一个 session。另外它保证了"服务 ready 时模型一定已加载"，不会出现前几个请求 503。`_session` 是模块级全局变量，lifespan 里赋值、predict 里读取。

**判分要点**
- `/predict` 返回 `label`、`confidence`、`probabilities` 三个字段，概率和为 1。
- 错误类型返回 4xx：类型不对 415、内容解析失败 400；不能 500。
- 服务未就绪时返回 503，而不是空指针崩溃。
- 10 次延迟都记录，给出中位数（不是均值，均值会被 4.8 ms 的偶发值拉高）。
- 能说清 lifespan 只加载一次、请求间共享 session。

**常见错误**
- 把 `ort.InferenceSession(...)` 写在 `predict()` 里，每次请求重新加载，延迟高一个量级。
- 只检查 `content_type`，不 try/except 解码，坏图直接 500。
- 预处理和训练不一致（训练是灰度 28×28 /255，服务里用了 RGB 或没 resize）。
- 用 `uvicorn app:app --reload` 上生产，reload 会重复加载模型。
- 延迟只测一次，没有 warmup，报出的是首次加载时间。

### 练习 8（推理优化对比）

**参考代码**
```bash
cd E:\AI学习\模块15_工程化与部署\code
python bench_infer.py
```

`bench_infer.py` 的计时协议：每个配置 warmup 5 次（batch 测试 warmup 3 次），计时 30 次（batch 测试 15 次），取中位数；GPU 计时前后 `torch.cuda.synchronize()`。

**实测输出**
```
device=cuda  torch=2.9.1+cu128
gpu=NVIDIA GeForce RTX 5060 Laptop GPU

[1] batch=1 fp32   no_grad=3.34 ms   with_grad=3.85 ms   加速 1.15x
[2] batch=1 fp16   3.98 ms   vs fp32 3.34 ms   加速 0.84x
    autocast 版      4.26 ms   加速 0.78x

    batch=  1     3.38 ms/批     296.2 张/秒
    batch=  8     8.31 ms/批     962.1 张/秒
    batch= 32    26.46 ms/批    1209.6 张/秒
    batch=128   107.37 ms/批    1192.1 张/秒

    普通           99.7 ms/step  峰值显存 1070.2 MB
    梯度检查点    101.9 ms/step  峰值显存 1025.0 MB   时间 1.02x  显存 1.04x
```

**逐条解释**

- **no_grad 在 bs=1 几乎不提速（1.15x）**：bs=1 时计算量太小，瓶颈在 kernel 启动、Python/调度开销和数据搬运，不在反向图的构建。省掉计算图对总时间影响有限。它的主要价值是**显存**：bs=32 时保留的中间激活差约 3 倍（讲义实测 257.1 MB vs 780.6 MB）。本次脚本没有单独测 bs=32 的 no_grad 显存，只测了训练态。
- **fp16 反而更慢（0.84x）**：ResNet18 在 224 输入、bs=1 时，fp16 的 kernel 启动和类型转换开销盖过了算力收益；张量核心需要足够大的矩阵才能吃满。小模型 + 小 batch 上 fp16 不划算。
- **channels_last 更慢（0.69x）**：channels_last 对 Tensor Core 卷积有利，但这里 batch=32、分辨率 224，且输入需要额外做 layout 转换；在本机这个尺度上转换成本大于收益。
- **梯度检查点几乎不省显存（1.04x）**：ResNet18 本身只有 11.7M 参数，激活不是瓶颈；`checkpoint_sequential` 切成 4 段，每段边界仍要保存，收益被摊薄。**梯度检查点适合"深且宽、激活占主导"的模型，不适合 resnet18 这种小骨干。**
- **吞吐平台期在 batch=32 附近**：296 → 962 → 1210 → 1192 张/秒，bs=32 与 bs=128 基本持平，说明 GPU 已吃满，再加大 batch 只增加延迟不增加吞吐。

**判分要点**
- 每个数字都是 warmup 后多次计时的中位数，不是单次。
- 同时给时间和峰值显存；只给时间不算完成。
- 能解释 no_grad 在 bs=1 的收益来自"省图"而不是"省计算"，主要价值在显存。
- 能指出吞吐平台在 bs=32 左右，并说明继续加 batch 的代价。
- 对"fp16 更慢""channels_last 更慢"这类反直觉结果，能给出本机尺度下的原因，而不是硬说"应该更快"。

**常见错误**
- 不做 warmup，第一次计时包含 cuDNN autotune，数字偏大数倍。
- GPU 计时不同步，测到的是"kernel 人队时间"不是执行时间。
- 只报平均不报中位数，偶发尖峰把均值拉高。
- 认为 fp16 一定更快；小模型/小 batch 上常常更慢。
- 把训练态的显存和推理态的显存混在一起比。
- 吞吐只测 bs=1，看不到平台期。
