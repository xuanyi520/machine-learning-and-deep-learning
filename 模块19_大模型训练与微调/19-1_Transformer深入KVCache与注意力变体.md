## 〇、这一节在解决什么

**16-1 你学过注意力：Q、K、V，算相似度，softmax，加权求和。**

**但有一个问题当时没讲：**

> **模型生成 100 个字，要算多少次注意力？**

**答案是：如果朴素地实现，算 5050 次。用 KV Cache，算 100 次。**

**差 50 倍。这就是为什么「大模型推理慢」这个问题，一半靠 KV Cache 解决。**

---

## 一、自回归生成：一次一个词

**大模型不是「一口气吐出整句话」，是「一次吐一个词，然后把它接到输入后面，再吐下一个」。**

```
输入：中国的首都是
  ↓
第 1 次：输出「北」
  ↓
输入：中国的首都是北
  ↓
第 2 次：输出「京」
  ↓
输入：中国的首都是北京
  ↓
第 3 次：输出「。」
```

**问题来了：每次输入都变长了。**

### 朴素实现的代价

**第 t 次生成时，要把前面 t 个 token 全部重新算一遍。**

**包括：**

```
① 重新投影出 Q、K、V（三个矩阵乘法）
② 用新的 Q 和全部 K 算相似度
③ 加权求和得到输出
```

**其中第 ① 步是纯浪费——前 t-1 个 token 的 K 和 V，上一次已经算过了，结果完全一样。**

---

## 二、KV Cache：算过就别再算

**核心思想一句话：把每一步算出来的 K 和 V 存起来，下一步直接用。**

```
第 1 步：算 token_1 的 K1、V1 → 存进 cache
第 2 步：只算 token_2 的 K2、V2 → cache 里变成 [K1, K2]
        Q2 直接和 [K1, K2] 算注意力
第 3 步：只算 token_3 的 K3、V3 → cache 里变成 [K1, K2, K3]
        Q3 直接和 [K1, K2, K3] 算注意力
```

**省掉的是「重复投影 K 和 V」这件事。**

### 实测收益

**我在本机跑了一个模拟（512 个 token，维度 64）：**

```python
import numpy as np

n = 512
# 不用 cache：每个 token 要重新投影 t 个 K/V
total_without = sum(t for t in range(n))
# 用 cache：K/V 只投影一次
total_with = n
```

**输出：**

```
不用 cache：总计 130,816 次投影
用 cache：  总计 512 次投影
投影次数减少: 255.5 倍
```

**255 倍。**

**这就是为什么同样是生成 512 个 token，有的实现要 30 秒，有的要 0.3 秒。**

### 为什么不是无限快

**省的是 K/V 投影，没省注意力打分。**

**注意力打分仍然是 O(n²)：第 t 步要算 t 次相似度。**

```
总打分次数 = 1 + 2 + 3 + ... + n = n(n+1)/2
```

**所以序列越长，注意力本身越贵。KV Cache 只能省掉其中一部分。**

---

## 三、代价：显存

**Cache 不是白来的。每个 token 都要在显存里存一份 K 和 V。**

### 计算公式

```
显存 = 序列长度 × 层数 × KV 头数 × 头维度 × 2（K和V）× 精度字节数
```

**实测（512 token，28 层，头维度 64，fp32）：**

```
4 个 KV 头  (GQA): 28.0 MB
28 个 KV 头 (MHA): 196.0 MB
```

**差 7 倍。**

**序列再长一点呢？**

| 序列长度 | MHA（28头） | GQA（4头） |
|---|---|---|
| 512 | 196 MB | 28 MB |
| 4096 | **1.57 GB** | 224 MB |
| 32768 | **12.5 GB** | 1.79 GB |

**看到问题了吗：**

> **32K 上下文时，光是 KV Cache 就要 12.5 GB。**
>
> **你的显卡一共才 8 GB。**

**这就是为什么「长上下文」这么贵，也是为什么有了 GQA。**

---

## 四、三种注意力变体

### MHA：Multi-Head Attention（标准版）

**每个注意力头都有自己独立的 Q、K、V。**

```
28 个头 → 28 组 K、V → cache 存 28 份
```

**效果最好，显存最贵。**

### MQA：Multi-Query Attention

**所有头共享同一组 K、V，只有 Q 各用各的。**

```
28 个 Q 头 → 只有 1 组 K、V → cache 存 1 份
```

**显存降到 1/28，但效果会掉。**

**Google 在 PaLM 上用过，后来不太流行了——掉得太明显。**

### GQA：Grouped-Query Attention（现在的主流）

**折中：把 28 个头分成 7 组，每组共享一组 K、V。**

```
28 个 Q 头 → 4 组 K、V → cache 存 4 份
```

**显存降到 1/7，效果接近 MHA。**

**LLaMA 2/3、Qwen、Mistral 全用 GQA。**

### 一张表对比

| | Q 头数 | KV 头数 | Cache 大小 | 效果 |
|---|---|---|---|---|
| MHA | 28 | 28 | 100% | 最好 |
| GQA | 28 | 4 | **14%** | **接近 MHA** |
| MQA | 28 | 1 | 3.6% | 明显下降 |

**面试常问：「为什么现在的模型都用 GQA？」**

**答案：它用 1/7 的显存拿到了接近 MHA 的效果。在长上下文场景下，这个取舍几乎是必然的。**

---

## 五、KV Cache 在训练时用吗

**不用。**

**训练时是一次性处理整个序列，所有位置的 Q/K/V 都是一次算出来的，不存在「重复计算」的问题。**

**而且训练时用了 teacher forcing——输入是整个句子，不是一步步生成。**

**所以：**

| 阶段 | 用 KV Cache 吗 |
|---|---|
| 训练 | ❌ 不用 |
| 推理（逐 token 生成） | ✅ 必用 |
| 推理（一次性处理，如分类） | ❌ 不用 |

**这个区分很重要。很多人以为「训练也用了 cache」，其实是混淆了。**

### 任务一：手写两个版本，对比

```python
import numpy as np

def attn_no_cache(Q, K, V):
    """朴素版：每次重算全部"""
    out = np.zeros_like(V)
    for t in range(Q.shape[0]):
        q = Q[t:t+1]
        s = q @ K[:t+1].T / np.sqrt(Q.shape[1])
        w = np.exp(s - s.max(-1, keepdims=True))
        w /= w.sum(-1, keepdims=True)
        out[t] = (w @ V[:t+1])[0]
    return out

def attn_with_cache(Q, K, V):
    """缓存版：K/V 只取一次"""
    cache_K, cache_V = [], []
    out = np.zeros_like(V)
    for t in range(Q.shape[0]):
        cache_K.append(K[t]); cache_V.append(V[t])
        Kc, Vc = np.stack(cache_K), np.stack(cache_V)
        s = Q[t:t+1] @ Kc.T / np.sqrt(Q.shape[1])
        w = np.exp(s - s.max(-1, keepdims=True))
        w /= w.sum(-1, keepdims=True)
        out[t] = (w @ Vc)[0]
    return out
```

**验证：**

```python
n, d = 512, 64
rng = np.random.default_rng(0)
Q, K, V = rng.normal(size=(n,d)), rng.normal(size=(n,d)), rng.normal(size=(n,d))

print(np.allclose(attn_no_cache(Q,K,V), attn_with_cache(Q,K,V), atol=1e-6))
```

**实测输出：**

```
True
```

**两个版本结果完全一样，但计算量差了 255 倍。**

## 十、常见错误

| 错误 | 现象 | 改法 |
|---|---|---|
| 以为 KV Cache 会改变输出 | 担心精度损失 | 它是数学等价优化 |
| 训练时也想用 cache | 无处可用 | 训练是一次性算完 |
| 只看参数量不看 KV 头数 | 估错显存 | 查 `num_key_value_heads` |
| 认为长上下文只受参数量限制 | 8 GB 跑不动 32K | KV Cache 才是瓶颈 |
| 混淆 Q 和 K/V 的缓存 | 理解错 | 只缓存 K 和 V，Q 每步都新算 |
