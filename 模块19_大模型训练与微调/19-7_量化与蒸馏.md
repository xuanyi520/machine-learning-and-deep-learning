## 一、量化：用更少的位数存同样的数

### 基本原理

**一个 fp16 的权重占 2 字节，能表示 65536 个不同的值。**

**但权重的实际分布很集中——大部分值在 -0.1 到 0.1 之间。**

**量化：把连续的值映射到有限的几个「桶」里。**

```
fp16:  -0.0234, 0.0156, 0.0089, -0.0421, ...
int8:  -6,      4,      2,      -11,      ...   （256 个桶）
int4:  -3,      1,      0,      -5,       ...   （16 个桶）
```

**存储时只存整数，计算时反量化回浮点。**

### 各精度的体积对比

**1.7B 模型：**

| 精度 | 每参数位数 | 权重大小 | 相对 fp16 |
|---|---|---|---|
| fp32 | 32 | 6.8 GB | 2× |
| **fp16 / bf16** | **16** | **3.4 GB** | **1×** |
| int8 | 8 | 1.7 GB | 0.5× |
| **int4** | **4** | **约 0.9 GB** | **0.26×** |

**int4 能压到 1/4 不到。**

### 代价：效果会掉

**掉多少取决于方法。好的量化方法能做到几乎无感。**

| 精度 | 典型效果损失 |
|---|---|
| fp16 → int8 | **几乎无损**（PPL 变化 < 0.5%） |
| fp16 → int4（简单方法） | 明显下降 |
| **fp16 → int4（GPTQ/AWQ）** | **1-3%** |

**所以：int8 基本可以无脑用，int4 要看方法。**

## 二、四种主流量化方法

### GPTQ

**思路：逐个「层级」地量化，每量化一层，就调整剩余未量化的权重来补偿误差。**

```
量化第 1 层 → 误差 e1
调整第 2..N 层的权重，让它们补偿 e1
量化第 2 层 → 误差 e2
...
```

**特点：**

- **需要校准数据**（几百条样本，跑一遍）
- 量化后模型**不能继续训练**
- 效果稳定，被广泛使用

### AWQ

**思路：不是所有权重都一样重要，**激活值大的通道**权重要保护。**

```
观察校准数据上每一层的激活分布
→ 找出「重要的」通道
→ 这些通道用更高精度，其余用低精度
```

**特点：**

- 也要校准数据
- **通常比 GPTQ 效果好一点**，尤其是小模型
- 现在很多模型发布时直接提供 AWQ 版本

### GGUF

**不是量化方法，是一个「文件格式」。**

**它把模型和量化打包成一个文件，可以在 CPU 上跑（也可以 GPU 加速）。**

**特点：**

- **llama.cpp / Ollama 用的就是它**
- 支持多种量化档位（Q2_K 到 Q8_0）
- **单文件，方便分发**
- **CPU 上也能跑**，这是最大的优势

**量化档位命名：**

```
Q4_K_M    ← 4 位，K 表示用了 K-quant 分组量化，M 表示中等
Q5_K_M    ← 5 位
Q8_0      ← 8 位，几乎无损
```

**`Q4_K_M` 是最常用的档位——体积和效果的平衡点。**

### bitsandbytes（在线量化）

**在加载模型时直接量化，不需要提前处理。**

**优点：方便，可以配合 LoRA 做 QLoRA。**

**缺点：**

- **Windows 上装不上**（19-3 提过）
- 只适合训练/实验，不适合生产部署

### 四种方法对比

| | GPTQ | AWQ | GGUF | bitsandbytes |
|---|---|---|---|---|
| 类型 | 量化方法 | 量化方法 | **格式** | 在线量化 |
| 要校准数据 | ✅ | ✅ | 转换时可选 | ❌ |
| 能 CPU 跑 | ❌ | ❌ | **✅** | ❌ |
| 能继续训练 | ❌ | ❌ | ❌ | ✅（配合 LoRA） |
| 适合 | GPU 部署 | GPU 部署 | **本地/边缘** | 训练实验 |

**你的场景（本地部署演示）：用 GGUF。**

## 三、蒸馏：用小模型学大模型

### 基本思想

**不是压缩大模型，而是训练一个小模型去模仿它。**

```
老师模型（7B，效果好，很大）
    ↓ 生成大量「问题-答案」
学生模型（1.7B，小，快）
    ↓ 在这些数据上训练
```

### 三种蒸馏

| 类型 | 学生学到了什么 |
|---|---|
| **输出蒸馏**（最简单） | 老师生成的答案（就是 SFT） |
| **软标签蒸馏** | 老师的**概率分布**（不只是一个词） |
| **特征蒸馏** | 老师中间层的表示 |

**软标签蒸馏的关键：**

**老师对「北京」给了 0.85，「中国首都」给了 0.10，「上海」给了 0.02。**

**这些「次优选项的概率」包含了「哪些答案比较接近」的信息，比硬标签信息量大得多。**

```text
硬标签：只知道答案是「北京」
    loss_hard = cross_entropy(student_logits, label)

软标签：知道整个分布
    loss_soft = KL(teacher_probs / T || student_probs / T) * T**2
```

**`T` 是温度，调高会让分布更平缓，信息更多。**

### 什么时候用蒸馏

| 场景 | 用蒸馏吗 |
|---|---|
| 有 7B 的钱，但推理要快 | ✅ |
| 要部署到手机/边缘设备 | ✅ |
| 只是想让模型小一点 | ⚠️ 量化更简单 |
| 想提升小模型能力 | ✅ 但需要大量数据和算力 |

**对你的情况：蒸馏的投入产出比不如量化。**

**1.7B 本来就不大，量化到 0.9 GB 足够用。**

## 四、实操：把 LoRA 模型转成 GGUF

**这是本节唯一需要动手的部分。**

### 步骤一：合并 LoRA

**第一步要把适配器和基座合并成完整模型。**

```
llamafactory-cli export export.yaml
```

**或者用 peft：**

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-1.7B", torch_dtype=torch.float16)
model = PeftModel.from_pretrained(base, "output/qwen3-1.7b-medical-lora")
model = model.merge_and_unload()
model.save_pretrained("models/qwen3-1.7b-medical-merged")
```

### 步骤二：转 GGUF

**需要 `llama.cpp` 的转换脚本。**

```
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp
pip install -r requirements.txt

python convert_hf_to_gguf.py ^
  --outfile models/qwen3-medical-f16.gguf ^
  --outtype f16 ^
  models/qwen3-1.7b-medical-merged
```

**这会生成一个 fp16 的 GGUF。**

### 步骤三：量化

```
cd llama.cpp
build/bin/quantize.exe ^
  models/qwen3-medical-f16.gguf ^
  models/qwen3-medical-Q4_K_M.gguf ^
  Q4_K_M
```

**Windows 上要先编译 llama.cpp，或者下载预编译的 release。**

### 步骤四：用 Ollama 跑

**最快的路径：直接写一个 Modelfile。**

```
FROM ./models/qwen3-medical-Q4_K_M.gguf

TEMPLATE """<|im_start|>system
你是一个医学影像助手。<|im_end|>
<|im_start|>user
{{ .Prompt }}<|im_end|>
<|im_start|>assistant
"""

PARAMETER temperature 0
PARAMETER stop "<|im_end|>"
```

```
ollama create qwen3-medical -f Modelfile
ollama run qwen3-medical
```

**这样就能在命令行里对话了。**

### 效果对比要测什么

**量化完必须验证：**

```python
# 同一批问题，量化前后各跑一次
for q in test_questions:
    ans_fp16 = model_fp16.generate(q)
    ans_q4 = model_q4.generate(q)
    print(f"问题: {q}")
    print(f"  fp16: {ans_fp16}")
    print(f"  Q4:   {ans_q4}")
    print(f"  是否一致: {ans_fp16 == ans_q4}")
```

**重点关注：**

- 医学事实有没有说错（数字、术语）
- 回答长度是否明显变短（量化有时会让模型变懒）
- 格式有没有坏

## 五、量化的实际影响

### 文件大小

**1.7B 模型：**

| 格式 | 大小 |
|---|---|
| fp16 | 3.4 GB |
| Q8_0 | 1.8 GB |
| **Q4_K_M** | **约 1.0 GB** |

### 速度

**不是所有量化都更快。**

| 场景 | Q4 比 fp16 快吗 |
|---|---|
| GPU 上（显存够） | ⚠️ 可能更慢（要反量化） |
| GPU 上（显存不够，原来要换出） | ✅ 明显快 |
| **CPU 上** | ✅ **快很多** |
| 移动端 | ✅ 必须量化 |

**关键：量化的主要收益是「能跑起来」，不是「跑得更快」。**

**如果你 8 GB 显存本来就能装下 fp16，量化不一定提速。**

### 效果

**实测经验（不同模型差异较大）：**

| 档位 | 典型效果损失 |
|---|---|
| Q8_0 | < 1% |
| Q5_K_M | 1-2% |
| **Q4_K_M** | **2-5%** |
| Q3_K_M | 5-10% |
| Q2_K | 明显崩坏 |

**医疗场景建议 Q5 起步，Q4 是底线。**

**不要用 Q3 以下。**
