## 一、三条原则

### ① 目录结构反映「数据的层级关系」，不是「你处理到哪一步了」

**错误做法：按处理阶段建目录。**

```
❌ raw/ cleaned/ normalized/ augmented/
```

**问题：** 同一批数据散在四个目录里，想找「病人 042 的所有版本」要翻四遍。

**正确做法：按数据本身的层级。**

```
✅ patients/
    └── ANON_a3f8c2/
        ├── study_20260115/
        │   ├── series_T1/
        │   └── series_T2/
        └── metadata.json
```

### ② 文件名要能自解释

**看文件名就知道：这是谁、什么时候、什么模态、什么处理。**

```
❌ IMG_0001.dcm
❌ 1.nii.gz
✅ ANON_a3f8c2_study20260115_T1_seg.nii.gz
```

### ③ 派生数据必须能追溯到源头

**每一个处理后的文件，都要能回答「我是从哪个原始文件、用什么脚本、什么参数做出来的」。**

## 二、目录结构：参考已有标准

**别自己发明。医学影像领域有几个成熟规范。**

### BIDS：脑影像的规范

**BIDS（Brain Imaging Data Structure）是脑影像领域的社区标准。**

```
dataset/
├── dataset_description.json       ← 元信息
├── participants.tsv                ← 病人表
├── participants.json               ← 表的字段说明
├── sub-01/
│   ├── anat/
│   │   ├── sub-01_T1w.nii.gz
│   │   └── sub-01_T1w.json
│   └── func/
│       └── sub-01_task-rest_bold.nii.gz
└── derivatives/                    ← 派生数据
    └── sub-01/anat/sub-01_T1w_seg.nii.gz
```

**关键设计：**

| 设计 | 好处 |
|---|---|
| `sub-XX` 作为一级目录 | 一个病人一个文件夹 |
| **模态和序列写在文件名里** | 不靠目录层级区分 |
| **每个数据文件配一个 `.json`** | 记录采集参数 |
| `derivatives/` 放派生数据 | 原始和处理分开 |

**你可以借用这个思想，即使不做脑影像。**

### 一套适用于任意医学影像的结构

```
项目根/
├── README.md                       ← 项目说明（别人第一眼看这个）
├── dataset_description.json        ← 元信息（版本、来源、伦理批号）
├── participants.tsv                ← 病人表（假 ID + 基本信息）
├── raw/                            ← 只读，永远不改
│   └── sub-ANON_a3f8c2/
│       └── ses-20260115/
│           ├── ct.nii.gz
│           ├── ct.json             ← 采集参数
│           └── seg_liver.nii.gz    ← 如果有标注
├── derivatives/                    ← 所有派生数据
│   ├── preprocessed_v1/
│   │   └── sub-ANON_a3f8c2/...
│   └── preprocessed_v2/
├── code/                           ← 所有脚本
│   ├── preprocess.py
│   ├── train.py
│   └── configs/
│       ├── preprocess_v1.yaml
│       └── train_v1.yaml
├── results/                        ← 实验输出
│   └── exp_20260301_unet_96cube/
│       ├── config.yaml
│       ├── metrics.json
│       └── predictions/
└── logs/
```

### 三条硬规矩

**① `raw/` 只读**

**任何处理都输出到 `derivatives/`。** 原始数据被改坏，整个项目重来。

**② `derivatives/` 的每一版带版本号**

```
preprocessed_v1/    ← 第一次预处理
preprocessed_v2/    ← 换了重采样参数
```

**不要覆盖。** 覆盖了就回不去了。

**③ 每个 `results/` 子目录必须带 `config.yaml`**

**跑完实验忘了参数，等于白跑。**

## 三、命名规范

### 一套可用的模板

```
{假ID}_{检查日期}_{模态}_{处理类型}_{版本}.{扩展名}

ANON_a3f8c2_20260115_CT_orig.nii.gz
ANON_a3f8c2_20260115_CT_seg.nii.gz
ANON_a3f8c2_20260115_CT_pre_v2.nii.gz
```

### 六个规则

| 规则 | 例子 |
|---|---|
| **只用小写字母、数字、下划线、连字符** | `anon_a3f8c2` ✅ / `Anon A3F8C2` ❌ |
| **不要空格** | `liver_ct.nii.gz` ✅ |
| **日期用 `YYYYMMDD`** | `20260115` ✅ / `2026-01-15` ❌ |
| **不用中文** | 跨平台、跨工具都可能出问题 |
| **字段顺序固定** | 所有文件同一个顺序，才能用正则解析 |
| **同一类文件扩展名统一** | 全用 `.nii.gz`，不要混用 `.nii` |

### 为什么不用空格和中文

**三个真实的坑：**

```
① 命令行里要转义：cp "my file.dcm" → 忘了引号就变成两个参数
② shell 脚本的 for 循环会把它拆成两个
③ 某些工具（尤其是老的 C 程序）直接报错
```

**中文还多一条：不同系统编码不一样，`ANON_张三` 在某些工具里会变成乱码文件名。**

### 批次号和日期不要混

**同一个病人做两次检查，日期不同。** 但如果是回顾性数据，可能同一天做了两个序列。

**建议：`病人ID + 检查日期 + 序列号`**

```
ANON_a3f8c2_20260115_s1_T1.nii.gz
ANON_a3f8c2_20260115_s2_T2.nii.gz
```

## 四、版本管理：git 管代码，DVC 管数据

### 为什么 git 不能管数据

**git 的每一个版本都存完整快照。**

```
一个 60 GB 的数据集，改了一次，版本历史变成 120 GB
```

**而且 git 会把整个文件读进内存做 diff，大文件直接卡死。**

### DVC 的做法

**DVC 只把「文件的哈希」存进 git，真实文件存在别处。**

```
git 里存的：
  data/images.dvc  → 内容是一行哈希：md5: d3f8c2a1...
  
真实文件在：
  本地缓存 / 网盘 / 对象存储
```

**工作流：**

```
dvc init
dvc add raw/                          # 生成 raw.dvc
git add raw.dvc raw/.gitignore
git commit -m "add raw data"

# 改了数据
dvc add raw/                          # 更新哈希
git commit -am "update raw data"

# 换台机器
git clone ...
dvc pull                              # 从远端拉真实数据
```

### 三种数据版本方案对比

| 方案 | 适合 | 缺点 |
|---|---|---|
| **目录版本号**（`data_v1/`、`data_v2/`） | **小项目、个人研究** | 占空间 |
| **DVC** | 正规项目 | 学习成本 |
| **DVC + 远端存储** | 团队 | 要配存储 |

**你现在的情况：目录版本号 + 一个 `CHANGELOG.md` 就够了。**

**不要为了用 DVC 而用 DVC。**

### 一个极简但有效的做法

```
data/
├── versions.md         ← 每个版本改了什么
├── v1_raw/             ← 原始
├── v2_preprocessed/    ← 重采样后
└── v3_final/           ← 最终用于训练
```

**`versions.md` 里写：**

```markdown
## v1_raw
2026-11-15
来源：某医院 2020-2023 回顾性数据，共 131 例
伦理批号：XXXX
状态：只读，永不修改

## v2_preprocessed
2026-11-20
脚本：code/preprocess.py，参数见 configs/preprocess_v1.yaml
变化：重采样到 1mm 各向同性，HU clip 到 [-200, 300]
与 v1 的差异：文件数 131 → 131（无缺失），平均体积增大 2.4 倍

## v3_final
2026-11-25
脚本：code/split.py
变化：按病人划分 train/val/test = 91/20/20
```

**这个文件比任何版本管理工具都重要。** 因为它写的是「为什么改」，工具只记得「改了什么」。

## 五、元数据索引表

**几千个文件时，光有目录结构不够。你需要一张能查的表。**

```python
import pandas as pd
from pathlib import Path

def build_index(root: Path) -> pd.DataFrame:
    """扫描目录，生成一张索引表"""
    rows = []
    for f in root.rglob("*.nii.gz"):
        parts = f.stem.replace(".nii", "").split("_")
        rows.append({
            "path": str(f.relative_to(root)),
            "patient": parts[0] if len(parts) > 0 else "",
            "date": parts[1] if len(parts) > 1 else "",
            "modality": parts[2] if len(parts) > 2 else "",
            "type": parts[3] if len(parts) > 3 else "",
            "size_mb": round(f.stat().st_size / 1024**2, 2),
        })
    return pd.DataFrame(rows)

df = build_index(Path("data/derivatives/preprocessed_v2"))
df.to_csv("data/index_v2.csv", index=False)

print(f"{len(df)} 个文件")
print(df.groupby("modality").size())
print(df.groupby("patient").size().describe())
```

**这张表能回答：**

- 有多少个病人
- 每个人的序列齐不齐
- 有没有异常大的文件
- 有多少缺失

**把它和 17-6 的质检结合起来，就是一个完整的「数据集说明书」。**

## 十、常见错误

| 错误 | 后果 | 改法 |
|---|---|---|
| 处理结果覆盖原始文件 | 无法回溯 | `raw/` 只读 |
| 文件名带空格或中文 | 脚本报错、乱码 | 只用小写英文数字下划线 |
| 版本靠 `final`/`final2` | 三个月后自己都懵 | 数字版本号 + changelog |
| 实验不存 config | 无法复现 | 每个 results 带 config.yaml |
| 一次上 DVC | 学习成本高 | 小项目先用目录版本 |
| 索引表不更新 | 和实际不符 | 每次处理完重新生成 |
