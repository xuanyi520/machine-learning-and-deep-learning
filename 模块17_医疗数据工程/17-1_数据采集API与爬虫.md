## 一、数据来源的三条路

**优先级从高到低，不要反过来。**

| 顺序 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **①** | **开放数据集** | 已授权、有标注、格式规范 | 可能不是你要的 |
| **②** | **官方 API** | 有文档、有配额、稳定 | 要申请 key |
| **③** | **网页爬虫** | 什么都能拿 | **法律和稳定性都是雷** |

**新手最常见的问题：一上来就想爬。**

**而实际上，医学领域 90% 的数据需求，前两条就能满足。**

### 优先找开放数据集

| 类型 | 去哪找 |
|---|---|
| 医学影像 | **MedMNIST**（你已经在用）、TCIA、Grand Challenge、Medical Segmentation Decathlon |
| 电子病历（脱敏） | MIMIC 系列（要考认证）、eICU |
| 文献全文 | PubMed Central Open Access、arXiv |
| 病理 | CAMELYON、TCGA |

**这些都已经过伦理审查和脱敏。用它们不违规。**

### 什么时候才需要 API

**比如你想批量拉 PubMed 的摘要做文献计量：**

```
https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi
  ?db=pubmed&term=liver+cancer&retmax=100&retmode=json
```

**NCBI 有官方的 E-utilities，不需要爬网页。**

### 什么时候才轮到爬虫

**目标站点没有 API、没有开放数据、而且 robots.txt 明确允许。**

**三个条件同时满足，才考虑。缺一个就换方案。**

## 二、第一件事：看 robots.txt

**这是技术问题之前的第一道关。**

```python
import urllib.robotparser as rb
import urllib.parse

UA = "XiaoYi-Research-Bot/1.0 (+mailto:你的邮箱)"

def can_fetch(url, user_agent=UA):
    """返回 True/False/None（None 表示读取失败）"""
    p = urllib.parse.urlparse(url)
    rp = rb.RobotFileParser()
    rp.set_url(f"{p.scheme}://{p.netloc}/robots.txt")
    try:
        rp.read()
    except Exception as e:
        return None, f"robots.txt 读取失败: {type(e).__name__}"
    return rp.can_fetch(user_agent, url), "ok"
```

**实测结果：**

```
https://pubmed.ncbi.nlm.nih.gov/   -> 允许
https://www.medmnist.com/          -> 允许
https://arxiv.org/abs/2401.00001   -> 允许
```

**这三个都是允许的，可以放心采。**

### 几个常见的坑

**坑一：robots.txt 只限制「爬虫」，不限制「人」**

**你可以手动打开浏览，但不代表程序可以批量抓。** 两者的区别是请求频率和对服务器的压力。

**坑二：返回 404 不代表没有限制**

**很多站点不设 robots.txt，但这不等于允许。** 看它的服务条款（Terms of Service）。

**坑三：403 / 需要登录的页面**

**这类页面爬取，多数情况下违反服务条款。** 别碰。

### 例外：明令禁止的领域

**以下三类别说 robots.txt 允许，就算全部允许也不能采：**

| 类型 | 为什么 |
|---|---|
| **含患者身份信息的数据** | 刑事风险 |
| **有版权的完整内容**（如论文全文 PDF 批量下载） | 民事风险 |
| **需要登录才能访问的私有数据** | 违反服务条款 |

## 三、API 调用的四个模式

### 模式一：分页

**几乎所有 API 都分页，因为一次返回太多会拖垮服务器。**

```python
def fetch_all_pages(base_url, params, max_pages=100):
    results = []
    page = 0
    while page < max_pages:
        params["page"] = page
        r = requests.get(base_url, params=params, timeout=30)
        r.raise_for_status()
        data = r.json()

        items = data.get("results", [])
        if not items:
            break                      # 没有更多了
        results.extend(items)

        if not data.get("next"):       # 有 next 字段就用它判断
            break
        page += 1
        time.sleep(0.5)                # 别打太急
    return results
```

**三个关键点：**

1. **`if not items: break`** —— 空页就停，别靠 `max_pages` 兜底
2. **`time.sleep(0.5)`** —— 每次请求之间停一下
3. **优先看文档里的 `next` 字段**，不要自己猜页码规则

### 模式二：限流

**大多数 API 有速率限制，比如「每分钟 60 次」。**

**超了会返回 429。** 处理方式：

```python
import time

def rate_limited_get(url, min_interval=1.0, **kwargs):
    """保证两次请求间隔不小于 min_interval 秒"""
    global _last_call
    now = time.time()
    wait = _last_call + min_interval - now
    if wait > 0:
        time.sleep(wait)
    _last_call = time.time()
    return requests.get(url, timeout=30, **kwargs)

_last_call = 0
```

**更稳妥的做法：直接看响应头里的配额信息。**

```python
r = requests.get(url)
print(r.headers.get("X-RateLimit-Remaining"))
print(r.headers.get("Retry-After"))
```

### 模式三：重试

**网络会抖，服务器会忙。不重试的脚本跑一千条能断十次。**

```python
import time
import requests

def fetch_with_retry(url, max_retry=3, timeout=15, **kwargs):
    for i in range(max_retry):
        try:
            r = requests.get(url, timeout=timeout, **kwargs)
            if r.status_code == 200:
                return r
            if r.status_code in (429, 500, 502, 503):
                wait = 2 ** i                   # 1s, 2s, 4s 指数退避
                print(f"  {r.status_code}, {wait}s 后重试")
                time.sleep(wait)
                continue
            return r                            # 4xx 不要重试，重试也没用
        except requests.RequestException as e:
            print(f"  异常 {type(e).__name__}, 重试")
            time.sleep(2 ** i)
    return None
```

**实测：**

```
PubMed 抓取: 成功, 状态 200, 内容长度 42373
```

**`4xx` 不重试这一条很重要。** 401（没权限）、404（不存在）重试一万次也是同样的结果。

### 模式四：断点续传

**跑了 800 条，第 801 条挂了，从头再来？**

```python
import json
from pathlib import Path

PROGRESS = Path("progress.json")

def load_progress():
    if PROGRESS.exists():
        return set(json.loads(PROGRESS.read_text()))
    return set()

def save_progress(done):
    PROGRESS.write_text(json.dumps(sorted(done)))

done = load_progress()
for item_id in all_ids:
    if item_id in done:
        continue
    ...
    done.add(item_id)
    if len(done) % 50 == 0:
        save_progress(done)
save_progress(done)
```

**医学数据采集动辄几十 GB，断点续传不是可选项，是必需品。**

## 四、网页解析三件套

**如果确实要爬，解析 HTML 用这三个。**

```python
# ① 优先：官方 API 或结构化数据
# 很多页面内嵌了 JSON-LD 或 __NEXT_DATA__，直接取比解析 HTML 稳得多

# ② BeautifulSoup：容错好，适合结构不规整的页面
from bs4 import BeautifulSoup
soup = BeautifulSoup(html, "lxml")
titles = [a.get_text(strip=True) for a in soup.select("h2.title a")]

# ③ lxml 的 XPath：快，适合结构清晰的页面
from lxml import html as lxml_html
tree = lxml_html.fromstring(html)
titles = tree.xpath("//h2[@class='title']/a/text()")
```

### 选择建议

| 场景 | 用什么 |
|---|---|
| 页面有内嵌 JSON | **直接正则抠 JSON，最稳** |
| 结构规整 | lxml + XPath |
| 结构乱、有缺失 | BeautifulSoup |
| 需要执行 JS | 上一节不够，见 17-2 |

**「页面有内嵌 JSON 就直接取」是最容易被忽略的一条。**

现代前端框架（Next.js、Nuxt）会把数据塞进 `<script id="__NEXT_DATA__">`，直接解析那个比解析 HTML 稳定十倍。

## 五、医疗数据的红线

**这一节比技术部分重要。**

### 绝对不能做的三件事

**① 采集患者的可识别信息**

```
姓名、身份证号、病历号、手机号、住址、面部照片、检查日期+罕见病组合
```

**即使只是「暂存」，也是违规。**

**② 绕过登录和权限**

**「技术上能做」和「被允许做」是两件事。**

**③ 把数据传到未经批准的地方**

**包括自己的私人云盘、第三方 AI 服务。**

### 可以做的前提

**必须同时满足：**

1. **有明确的授权**（伦理批件、数据使用协议）
2. **在授权范围内使用**（只用于研究、不商用）
3. **先脱敏再留存**（17-3 会讲怎么做）
4. **有访问日志**（谁在什么时候拿走了什么）

**这四条缺一不可。**

## 十、常见错误

| 错误 | 后果 | 改法 |
|---|---|---|
| 一上来就爬 | 法律风险 + 白费功夫 | 先找开放数据集和 API |
| 不看 robots.txt | 被封 IP | 第一步就查 |
| 4xx 也重试 | 无限循环 | 只重试 5xx 和 429 |
| 请求之间不睡眠 | 服务器扛不住、被封 | 至少 sleep 0.5 |
| 没有断点续传 | 断一次从头来 | 存 progress.json |
| 采集时带上病人信息 | **刑事风险** | 采集阶段就脱敏 |
| 用固定 User-Agent | 容易被识别成爬虫 | 带联系方式的自定义 UA |
