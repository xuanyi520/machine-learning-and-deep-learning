# 毕业项目 · 医学影像 AI 助手

**建议用时：52 小时（约 3 周）**

**这是整个模块的终点，也是简历上要放的那一行。**

---

## 〇、这个项目是什么

**一句话：给一张胸部 X 光片，输出一份带依据的结构化影像提示报告。**

**不是诊断，是「提示」。** 措辞问题 16-8 讲过，法律层面很重要。

### 完整链路

```
用户上传影像
    │
    ▼
① 预处理层     DICOM 读取 → HU 换算 → 窗宽窗位 → 归一化
    │
    ▼
② 影像模型层   你模块 4-2 训的肺炎分类模型 → 概率 + 置信度
    │
    ▼
③ 知识检索层   RAG 查指南：「肺炎的影像学表现」「肺炎的鉴别诊断」
    │
    ▼
④ 编排层       Agent 决定：要不要调检索？调哪个？结果够不够？
    │
    ▼
⑤ 生成层       VLM 综合影像结论 + 指南依据 → 结构化报告
    │
    ▼
⑥ 服务层       FastAPI 对外提供 POST /analyze
    │
    ▼
带引用的结构化报告
```

**每一层对应你学过的一节：**

| 层 | 对应 |
|---|---|
| ① 预处理 | 模块 4-1（DICOM、HU、窗宽窗位） |
| ② 影像模型 | 模块 4-2（肺炎分类） |
| ③ 知识检索 | 16-4（RAG） |
| ④ 编排 | 16-5 / 16-6（Agent、LangGraph） |
| ⑤ 生成 | 16-2（结构化输出）、16-8（VLM） |
| ⑥ 服务 | 16-9（FastAPI、Docker） |

**这个项目的价值就在这：把学过的每一块串起来，而不是又造一个孤立的 demo。**

## 一、为什么选这个题目

**和同类项目比，它的差异点在哪：**

| 常见项目 | 问题 | 这个项目的不同 |
|---|---|---|
| MNIST 手写数字 | 太简单，面试官不看 | 真实医学数据 |
| 猫狗分类 | 和你的专业无关 | 医疗场景 |
| 「基于 LangChain 的问答机器人」 | 没有专业壁垒，谁都能做 | **有医学影像模型做底座** |
| 「肝癌预测」纯表格 | 没有深度学习的部分 | 影像 + 文本多模态 |
| 「ChatGPT 套壳」 | 没有算法含量 | 有自己训的模型 |

**最核心的差异：**

> **别人做 Agent 应用，底座是通用模型。你的底座是你自己训的医学影像模型。**
>
> **这是「算法岗」和「应用岗」的分界线。**

## 二、技术选型（以及为什么这么选）

| 组件 | 选什么 | 为什么 | 备选 |
|---|---|---|---|
| 影像模型 | 你自己的 ResNet / DenseNet | 必须是自己的 | —— |
| 生成模型 | `deepseek-flash` | 便宜、支持图片、1M 上下文 | qwen-plus |
| 检索 | TF-IDF + embedding 混合 | 医学缩写必须精确匹配 | 纯向量 |
| 文本向量 | `BAAI/bge-small-zh-v1.5` | 中文好、95 MB、本地跑 | text2vec |
| 编排 | 手写 Agent，可选 LangGraph | 先手写才懂原理 | LangGraph |
| 服务 | FastAPI | 已有、自动文档 | Flask |
| 部署 | Docker Compose | 已有 | 裸机 |

**为什么不全用 LangChain：**

> **面试官会问「不用框架的话你怎么实现」。答不上来说明你只会调包。**

**建议：先手写一版（16-5 的代码），跑通之后再用 LangGraph 重构一版。两版都留着，面试时可以对比讲。**

## 三、分阶段实施

**不要一次全写。每完成一个阶段都是一个能演示的东西。**

### 阶段一：跑通主干（12 小时）

**目标：一张图进去，一个概率出来，走 HTTP。**

- [ ] 把模块 4-2 的模型保存成 `.pt`
- [ ] 写 `src/image_model/predict.py`，输入图片路径，输出概率
- [ ] 用 16-9 的 FastAPI 模板包起来
- [ ] `curl` 能调通

**这个阶段做完，你已经有一个能交付的服务了。** 哪怕后面全都不做，这个也能写进简历。

**验收：**

```
curl -X POST localhost:8000/predict -F "file=@test.png"
{"probability": 0.87, "label": "肺炎", "model_version": "v1.0"}
```

---

### 阶段二：加上知识检索（14 小时）

**目标：报告里每条结论都有依据。**

- [ ] 找一份《肺炎诊疗指南》，用 anymd 转 markdown
- [ ] 按 16-4 的方法切分、建索引
- [ ] 写 10 条测试问题，算 Recall@3
- [ ] **Recall@3 必须 > 70% 才能进下一阶段**

**为什么要卡这一关：** 检索不准，后面生成的报告全是错的。**这是整个项目的地基。**

**验收：**

- [ ] `knowledge_base/` 里有 ≥ 30 个片段
- [ ] `results/检索评估.md` 里有 Recall@3 具体数字和 10 条测试明细
- [ ] 问一个知识库里没有的问题，返回「未找到」

---

### 阶段三：编排起来（14 小时）

**目标：一个 Agent 能自己决定调什么。**

- [ ] 定义三个工具：`predict_image`、`search_guideline`、`get_hu_window`
- [ ] 写系统提示，约束流程
- [ ] 加工作记忆、重复检测、步数上限（16-5 的三道防线）
- [ ] 跑通四个测试场景

**验收：**

- [ ] 简单问题（「这张图有肺炎吗」）只调用 1 次工具
- [ ] 复杂问题（「有肺炎的话该怎么处理」）调用 2-3 次
- [ ] 知识库外的问题不编，说找不到
- [ ] 所有执行都有 trace，能复盘

---

### 阶段四：生成报告 + 服务化（12 小时）

**目标：对外提供一份完整的报告。**

- [ ] 用 16-2 的 JSON 结构化输出
- [ ] 每条结论带 `[编号]` 引用
- [ ] 校验编号真实性（16-4 第六节）
- [ ] 加 `/health`、错误处理、超时
- [ ] 写 Dockerfile 和 docker-compose.yml
- [ ] 压测出 P50/P95

**验收：**

- [ ] `docker compose up` 一条命令起全套
- [ ] `/docs` 能打开并交互调用
- [ ] 报告里每个 `[n]` 都真实存在
- [ ] P95 有具体数字

## 四、评估方案（这是最容易被忽略、也最能拉开差距的）

**大部分人做完项目就完了。你要能说出「这个系统有多好」。**

### 四层评估

| 层 | 指标 | 怎么测 |
|---|---|---|
| **① 影像模型** | AUC、灵敏度、特异度 | 你的测试集 |
| **② 检索** | Recall@3、Precision@3 | 10 条带标注的测试问题 |
| **③ 端到端** | 报告正确率 | 人工看 20 份 |
| **④ 性能** | P50、P95、吞吐 | 压测 100 次 |

### 第三层怎么做

**人看不现实，做一个「关键点核对表」：**

```python
CHECKLIST = [
    "是否给出了肺炎的概率",
    "概率是否和模型输出一致",
    "是否引用了至少一条指南",
    "引用的编号是否真实存在",
    "是否包含免责声明",
    "有没有出现『诊断』二字",      # 法律风险
]
```

**20 份报告，逐条打勾，算通过率。**

**这个表本身就是个很好的产出——面试时拿出来，比说「效果还不错」强一百倍。**

### 还必须做：失败分析

**至少 5 个失败案例，每个写清：**

```
【失败案例 1】
输入：某张片子
期望：提示肺炎
实际：提示正常
原因：模型漏诊（影像模型 AUC 不足）
归属层级：第 ② 层
能不能修：加数据 / 换模型 / 调阈值
```

**把失败归到具体层级，是工程能力的体现。**

## 六、给面试官怎么讲

**准备三个版本：30 秒、3 分钟、15 分钟。**

### 30 秒版（自我介绍里用）

> 我做过一个医学影像辅助提示系统。底层是我自己训练的肺炎分类模型，
> 上面接了一层基于指南知识库的检索，最外面用 Agent 编排，
> 输出带引用的结构化提示报告，用 Docker 打包成 HTTP 服务。

### 3 分钟版（技术面开场）

**按「为什么 → 怎么做 → 卡在哪 → 怎么解决」讲：**

```
为什么：现有影像 AI 只输出一个概率，医生不知道依据，不敢用。
       我的想法是：模型给客观结论，检索给依据，两件事分开。
怎么做：四层。预处理 → 影像模型 → RAG → Agent 编排。
       影像模型是 ResNet18 微调，测试集 AUC 0.XX。
       检索用的是 TF-IDF 和 bge 混检，Recall@3 是 XX%。
卡在哪：一开始 Recall@3 只有 50%，发现是切分把关键句切断了。
怎么解决：改成按标题结构切 + 100 字重叠，提到 78%。
```

### 15 分钟版（深挖）

**准备回答这些：**

| 问题 | 你要能答 |
|---|---|
| 为什么不用现成的多模态大模型直接看图 | 讲四道坎（16-8），讲 HU 信息丢失 |
| 检索为什么用混合而不是纯向量 | 医学缩写必须精确匹配 |
| Agent 怎么防止死循环 | 三道防线 |
| 报告会不会编 | 编号校验 + 人工核对表 |
| 如果上线，最大的风险是什么 | 假阳性 + 法律风险 |
| 你测了什么 | 四层评估，每层有具体数字 |

## 七、简历怎么写

**不要写成这样：**

```
基于大模型的医学影像辅助诊断系统
- 使用 LangChain 搭建 Agent
- 接入 RAG 检索
- 部署为 Web 服务
```

**问题：全是「用了什么」，没有「做到了什么」。**

**应该这样写：**

```
医学影像辅助提示系统（个人项目）
- 自训 ResNet18 肺炎分类模型，测试集 AUC 0.XX，推理 P95 XX ms
- 构建指南知识库（XX 篇，XX 个片段），采用结构切分 + 混合检索，
  Recall@3 达 XX%
- 手写 Agent 编排循环（含记忆、重复检测、步数上限），
  平均 XX 次工具调用完成一次完整分析
- FastAPI + Docker 部署，端到端 P95 XX s
```

**差别在哪：每一个技术点后面都跟着一个数字。**

**数字不用很漂亮。** 就算 Recall@3 只有 65%，写出来也比不写强——**不写数字，面试官会认为你没测过。**

## 九、常见失败模式

| 失败 | 表现 | 预防 |
|---|---|---|
| **一直在调模型** | 卡在阶段一，AUC 从 0.94 调到 0.95 | **先跑通全链路再优化** |
| 检索不测 | 报告看着像那么回事，其实全错 | 阶段二卡 Recall@3 门槛 |
| 没有数字 | 说不出效果 | 每一阶段都记指标 |
| 报告编造引用 | `[5]` 但只有 3 条 | 编号校验 |
| 措辞越界 | 写了「诊断为肺炎」 | 全文搜「诊断」 |
| 只做不写 | 代码能跑，README 空的 | README 当交付物写 |

**第一条最常见。** 很多人做项目，前 80% 的时间花在让模型从 0.94 到 0.95，后 20% 草草收尾。

**正确比例：模型 20%，工程 80%。** 因为面试官看的是「你能把东西做出来」，不是「你的模型多强」。

## 十、时间不够怎么办

**如果只剩一周：**

| 优先级 | 做什么 | 能砍什么 |
|---|---|---|
| 必做 | 阶段一（影像模型 + API） | 全部 |
| 必做 | 阶段二的检索 + Recall@3 | 混合检索可以只做 TF-IDF |
| 必做 | 阶段四的服务化 | Docker 可以不做 |
| 可砍 | 阶段三的 Agent | 改成固定流程：先预测，再检索，再生成 |
| 可砍 | 端到端评估 | 但失败案例要留 |

**砍掉 Agent 之后，项目描述改成：**

```
影像分类 → 知识检索 → 报告生成 的流水线
```

**不要说「Agent」，因为没有自主决策。** 说了面试官一追问就露馅。

**诚实比包装重要。**
