# 16-5 Agent 范式：ReAct 与规划

**建议用时：10 小时**

**出口标准：不用任何框架，手写一个能自主决定「下一步干什么」的 Agent，并说清它为什么会死循环。**

---

## 〇、这一节在解决什么

16-3 你写过一个工具调用循环：

```python
while True:
    resp = 调用模型(...)
    if resp 没要工具:
        break
    执行工具，把结果塞回去
```

**这段代码其实已经是 Agent 了。**

但你写它的时候，脑子里是「调用一次工具就完了」。而一个真正的 Agent 要面对的是：

```
问题：帮我分析这个病人的肝癌风险，并给出治疗建议
     ↓
它需要自己决定：
   - 先查 AFP 还是先查影像？
   - 查到 AFP 高了，下一步查什么？
   - 分期查出来了，治疗方案从哪找？
   - 资料里没有这一条，是换个查法还是直接说找不到？
```

**这些决定，你一个都没有写进代码。是模型在每一步自己做的。**

这就是 Agent 和普通程序的分界线。

---

## 一、先说清楚：Agent 和工具调用的区别

**这是面试高频问题，也是很多人概念混乱的地方。**

| | 工具调用（16-3） | Agent（本节） |
|---|---|---|
| 谁决定用几个工具 | 你大概知道，一次通常是 1 个 | **模型自己决定，可能 0 个也可能 10 个** |
| 循环几轮 | 通常 1-2 轮 | 不确定 |
| 谁决定下一步 | 你的代码顺序 | **模型根据上一步结果决定** |
| 有状态吗 | 基本没有 | **有，要维护记忆** |
| 失败怎么办 | 报错退出 | **要能重试、换路、放弃** |

**一句话：**

> **工具调用是「你让它做一件事」。Agent 是「你给它一个目标，它自己拆成几件事」。**

**注意：这个区别是程度上的，不是有无上的。** 16-3 的循环加上 `max_steps`，本身就是一个最简的 Agent。

---

## 二、ReAct：最容易理解的 Agent 范式

### 名字的来源

**Re**asoning + **Act**ing。**推理和行动交替进行。**

2022 年的一篇论文提出，思路朴素得出奇：

```
把「思考」这一步也写进模型的输出里，让它下一步的行动基于自己的思考。
```

### 循环长这样

```
问题
 │
 ▼
┌─────────────────────────────┐
│  Thought: 我需要先查一下 AFP │   ← 思考
│  Action:  lookup("AFP")     │   ← 行动
│  Observation: 45 ng/mL      │   ← 结果（你塞回去的）
└─────────────────────────────┘
 │
 ▼
┌─────────────────────────────┐
│  Thought: AFP 偏高，要查分期 │
│  Action:  lookup("BCLC分期") │
│  Observation: C 期           │
└─────────────────────────────┘
 │
 ▼
  Final Answer: ...
```

**关键点：`Thought` 也是模型自己生成的文字。**

**为什么有效**：模型多写了这几个字，下一步的决策就是在更多上下文上做的。**和 16-2 讲的 CoT 是同一个道理。**

### 用不用写 Thought

**你用的 `deepseek-flash` 是推理模型，它自带 `thinking` 块。**

所以你**不需要**在提示词里手动让格式化成 `Thought: ... Action: ...`。

**但知道这个格式有用**，因为：
1. 面试会问 ReAct 是什么
2. 换到不支持 thinking 的模型上，你得手写

## 三、手写一个 Agent

**不用 LangChain，不用 LangGraph。就 `requests` + `json`。**

### 代码

```python
import os, json, requests

URL = "https://api.deepseek.com/anthropic/v1/messages"
HEADERS = {
    "x-api-key": os.environ["DEEPSEEK_API_KEY"],
    "anthropic-version": "2023-06-01",
    "content-type": "application/json",
}

# ========== 1. 工具 ==========
KB = {
    "afp": "AFP 参考上限 7 ng/mL，超过 400 ng/mL 高度提示原发性肝癌。",
    "bclc": "BCLC 分期：0期极早期，A期早期，B期中期，C期晚期，D期终末期。"
            "C期对应门静脉侵犯或肝外转移，推荐系统治疗。",
    "treatment": "早期首选手术切除或消融。中晚期考虑TACE、靶向药物和免疫治疗。",
}

def lookup(topic: str) -> dict:
    key = topic.lower().strip()
    if key in KB:
        return {"topic": key, "content": KB[key]}
    return {"error": f"知识库中没有 '{topic}'，可用主题：{list(KB)}"}

TOOL_IMPL = {"lookup": lookup}

TOOLS = [{
    "name": "lookup",
    "description": "在本地医学知识库里查一个主题。可用主题：afp（甲胎蛋白标准）、"
                   "bclc（肝癌分期）、treatment（治疗方案）。"
                   "查不到时会返回可用主题列表。",
    "input_schema": {
        "type": "object",
        "properties": {"topic": {"type": "string", "description": "主题关键词"}},
        "required": ["topic"],
    },
}]

# ========== 2. 系统提示 ==========
SYSTEM = """你是一个医学知识助手，可以调用 lookup 工具查资料。

工作方式：
1. 先把问题拆成需要查的几个主题
2. 逐个调用 lookup
3. 如果 lookup 说没找到，可以换个关键词再试一次，但同一个关键词不要试超过两次
4. 资料够了就给出答案，并标注依据来自哪个主题

重要：
- 知识库里没有的，直接说不知道，不要编
- 不要超过 8 步"""

# ========== 3. Agent 循环 ==========
def run_agent(question, max_steps=8, verbose=True):
    messages = [{"role": "user", "content": question}]
    trace = []                                   # 记录每一步，方便事后看

    for step in range(1, max_steps + 1):
        resp = requests.post(URL, headers=HEADERS, json={
            "model": "deepseek-flash",
            "max_tokens": 2000,
            "temperature": 0,
            "system": SYSTEM,
            "tools": TOOLS,
            "messages": messages,
        }, timeout=180).json()

        messages.append({"role": "assistant", "content": resp["content"]})

        # 完成
        if resp.get("stop_reason") != "tool_use":
            answer = "".join(b["text"] for b in resp["content"]
                             if b["type"] == "text")
            if verbose:
                print(f"  步骤 {step}: 给出答案")
            return answer, trace

        # 执行工具
        results = []
        for b in resp["content"]:
            if b["type"] != "tool_use":
                continue
            args = b["input"]
            try:
                out = TOOL_IMPL[b["name"]](**args)
            except Exception as e:
                out = {"error": f"{type(e).__name__}: {e}"}

            trace.append({"step": step, "tool": b["name"],
                          "args": args, "result": out})
            if verbose:
                print(f"  步骤 {step}: {b['name']}({args}) -> {str(out)[:60]}")

            results.append({
                "type": "tool_result",
                "tool_use_id": b["id"],
                "content": json.dumps(out, ensure_ascii=False),
            })

        messages.append({"role": "user", "content": results})

    return "达到最大步数，未完成。", trace


# ========== 4. 跑 ==========
if __name__ == "__main__":
    q = "这个病人 AFP 45，想了解一下肝癌分期和治疗方案"
    answer, trace = run_agent(q)
    print("\n" + "=" * 50)
    print(answer)
    print("\n" + "=" * 50)
    print(f"共 {len(trace)} 次工具调用")
```

### 和 16-3 的代码比，多了什么

| 多了什么 | 在哪 | 为什么 |
|---|---|---|
| `system` 提示 | 请求里 | **告诉它工作方式**，这是最关键的改动 |
| 温度 = 0 | 请求里 | 决策要可复现 |
| `max_steps=8` | 循环 | 防死循环 |
| `trace` | 循环里 | **事后能复盘它每一步干了什么** |
| 提示词里写「换个关键词」「不要超过 8 步」 | SYSTEM | 主动约束行为 |

**注意：真正让它「像 Agent」的，是那段 `SYSTEM` 提示。代码结构和 16-3 几乎一样。**

## 四、Agent 的行为，全靠系统提示定义

**这一节最重要的一句话：**

> **Agent 的「智能」不在代码里，在你写的系统提示里。**

### 四条必备约束

**① 工作流程**

```
我的拆解流程：
1. 先判断问题涉及哪几个主题
2. 逐个查询，每次只查一个
3. 查到足够信息就回答
```

**不写会怎样**：它可能一次并发查 5 个，也可能一个都不查直接答。

**② 失败处理**

```
如果工具返回 error：
- 换一个等价的关键词再试一次
- 同一个关键词最多试两次
- 两次都不行，就在答案里说明「未能查到 X」
```

**不写会怎样**：它可能对着同一个关键词无限重试，直到步数耗尽。

**③ 停止条件**

```
资料足够回答问题时就停止，不要为了「更完整」而继续查。
```

**不写会怎样**：它会一直查到步数上限，白烧钱。

**④ 不知道就说不知道**

```
知识库里没有的信息，直接说不知道，不要补充你训练时的知识。
```

**不写会怎样**：**它会用训练数据里的一般医学知识回答，而且听起来很专业，但和你的知识库对不上。** 这在医疗场景是灾难。

## 五、Plan-and-Execute：另一种范式

### ReAct 的问题

**边想边做。** 每做一步都要调一次模型。

```
查 AFP（1 次调用）→ 想（1 次）→ 查分期（1 次）→ 想（1 次）→ 查治疗（1 次）→ 回答（1 次）
共 6 次
```

**问题：**

1. **贵**：每一步都带全部上下文
2. **容易跑偏**：中途想到别的就拐走了
3. **不可控**：你不知道它下一步要干什么，没法干预

### Plan-and-Execute 的做法

**先一次性把计划定好，再按计划执行。**

```
第一步（1 次调用）：给出计划
   1. 查 AFP 标准
   2. 查 BCLC 分期
   3. 查治疗方案

第二步（按计划执行，可以并发）：
   查 AFP → 查分期 → 查治疗

第三步（1 次调用）：根据全部结果写答案
共 5 次调用
```

### 两种范式对比

| | ReAct | Plan-and-Execute |
|---|---|---|
| 决策时机 | 边走边想 | 先想完再走 |
| 调用次数 | 多 | 少 |
| 灵活性 | **高**（能随机应变） | 低（计划定了就不改） |
| 可干预 | 差 | **好**（计划可以先给人看） |
| 适合 | 探索性任务 | **流程相对固定的任务** |

**你的医学场景更适合哪个？**

> **Plan-and-Execute。** 因为「查 AFP → 查分期 → 查治疗」这个顺序是临床上固定的。让模型自己发现这个顺序，纯属浪费。

**但 ReAct 也不是没用**：用户问一个开放性问题时（「帮我看看这个病人还有什么风险」），Plan 定不出来，得用 ReAct。

### 一个混合做法：先 Plan 再 ReAct

```
1. 让模型先输出一个计划（纯文本，不执行）
2. 打印出来给人看，可以改
3. 按计划执行，每一步内部用 ReAct 处理意外
```

**16-6 的 LangGraph 就是为这种结构设计的。**

## 六、Memory：Agent 的记忆

### 为什么需要

**你说「再查一下 C 期」，它得知道「C 期」指的是什么。**

**Agent 的对话会很长，上下文会爆。**

### 三种记忆

| 类型 | 存什么 | 怎么存 |
|---|---|---|
| **短期** | 当前对话的全部消息 | 就在 `messages` 列表里 |
| **工作记忆** | 已经查到的事实 | **单独抽取成结构化数据** |
| **长期** | 跨会话的知识 | 向量库（16-4） |

### 工作记忆最有用

**不要只把工具结果留在 `messages` 里。抽出来。**

```python
class Memory:
    def __init__(self):
        self.facts = {}          # 已确认的事实
        self.tried = {}          # 试过的查询 -> 结果

    def add_fact(self, key, value):
        self.facts[key] = value

    def was_tried(self, query):
        return query in self.tried

    def to_prompt(self):
        if not self.facts:
            return ""
        lines = [f"- {k}: {v}" for k, v in self.facts.items()]
        return "【已确认信息】\n" + "\n".join(lines)
```

**每一步把 `memory.to_prompt()` 拼进系统提示：**

```python
system = SYSTEM + "\n\n" + memory.to_prompt()
```

**好处：**

1. **防重复查询**：`was_tried()` 一查就知道，不用靠模型自己记得
2. **压缩上下文**：查到的事实只有一两行，比完整的工具返回省得多
3. **可审计**：事后能看到它到底确认了哪几条事实

## 七、三大杀手

**这是 Agent 落地最常见的三种翻车方式。** 你以后做项目一定会遇到。

### 杀手一：死循环

**表现：**

```
步骤 1: lookup("肝癌")  -> 没找到
步骤 2: lookup("肝癌")  -> 没找到
步骤 3: lookup("肝癌")  -> 没找到
...
```

**原因**：模型忘了自己试过，或者工具返回的 error 信息让它以为「多试几次就好了」。

**三道防线：**

```python
# 1. 步数上限（必须有）
for step in range(max_steps):

# 2. 重复检测
seen = set()
if (tool_name, json.dumps(args, sort_keys=True)) in seen:
    out = {"error": "你已经用相同参数调用过这个工具，结果不会变。请换个思路。"}
seen.add(...)

# 3. 同一工具连续失败上限
fail_count = 0
if out.get("error"):
    fail_count += 1
    if fail_count >= 3:
        return "工具连续失败 3 次，停止。"
```

**第二道最关键。** 它不只是拦截，还**告诉模型「结果不会变」**，模型往往就换思路了。

### 杀手二：上下文爆炸

**表现：**

```
第 1 步: input_tokens = 500
第 5 步: input_tokens = 8000
第 8 步: input_tokens = 35000      ← 每一步都重新发全部历史
```

**原因**：工具返回的内容很长（比如检索到 5 段各 800 字），每轮都重发。

**三道防线：**

```python
# 1. 工具返回截断
def lookup(topic):
    ...
    content = KB[key]
    if len(content) > 1000:
        content = content[:1000] + "...[已截断]"
    return {"content": content}

# 2. 用工作记忆压缩历史（见上一节）
#    查到的事实只留一两行，不留原文

# 3. 超过阈值就重启上下文
if estimate_tokens(messages) > 20000:
    summary = 让模型总结前面的结论
    messages = [{"role": "user", "content": f"【之前的进展】{summary}\n继续："}]
```

**第 3 条你其实踩过坑。** 之前那种「一直在思考」的现象，根因就是上下文涨到 21 万 token 后压缩失败，之后每条消息都拖着全部历史。

### 杀手三：工具失败级联

**表现：**

```
工具 A 失败 → 模型换个参数重试 → 又失败 → 模型认为是 B 的问题 → 去调 B
→ B 也失败 → 模型开始瞎猜 → 给出错误答案，但语气很自信
```

**原因**：一个基础工具坏了，模型不知道，会一路错下去。

**两道防线：**

```python
# 1. 关键工具失败，直接终止，不要让它继续
CRITICAL = {"lookup_patient"}
if tool_name in CRITICAL and out.get("error"):
    return f"关键工具 {tool_name} 失败，中止：{out['error']}"

# 2. error 里写清楚「下一步该干什么」
return {"error": "数据库连接超时。这是服务端问题，重试无用，请告知用户稍后再试。"}
```

**第 2 条很有效。** **在错误信息里写指令**，模型会照着做。

### 练习 16-5-C（必做）：写一版 Plan-and-Execute

**两阶段：**

1. 第一次调用，让模型只输出计划（纯文本列表，不调工具）
2. 打印计划，人工看一眼
3. 按计划逐条执行
4. 最后汇总

**对比 ReAct 版：调用次数少了多少？答案质量差了吗？**

### 练习 16-5-D（选做）：加一个人工确认点

**在执行有副作用的工具之前，停下来问用户：「要执行 X 吗？(y/n)」**

| 错误 | 表现 | 改法 |
|---|---|---|
| 系统提示只写「你是助手」 | 行为完全不可控 | 写清流程、失败处理、停止条件 |
| 不设 max_steps | 烧钱 | 必须有 |
| 工具返回原样塞回历史 | 上下文几步就爆 | 截断到 1000 字内 |
| error 只写「失败」 | 模型盲目重试 | 写清原因和下一步 |
| 没有 trace | 出问题完全没法查 | 每一步都记 |
| 用 ReAct 做固定流程 | 贵且慢 | 改用 Plan-and-Execute |
| 认为模型会「记得」 | 重复查询 | 用代码记，不靠模型 |
