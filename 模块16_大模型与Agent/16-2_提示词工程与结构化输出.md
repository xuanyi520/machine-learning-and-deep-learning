# 16-2 提示词工程与结构化输出

**建议用时：6 小时**

**出口标准：能让模型稳定输出可被 `json.loads()` 解析的 JSON，连续 20 次不崩。**

---

## 〇、这一节在解决什么

上一节你学会了怎么把话发给模型。问题是：**它每次回的格式都不一样。**

同一个问题，它可能回：

```
肺部用肺窗。
```

也可能回：

```
观察肺部时，通常使用**肺窗**（Lung Window），
窗宽约 1500 HU，窗位约 -600 HU。
```

**人看着都没问题，代码没法处理。**

这一节要解决的就是：**怎么让它的输出变成程序能吃的东西。**

---

## 一、提示词不是「说话技巧」，是「接口定义」

很多人把提示词当成「怎么问它才听话」。这个理解不完整。

**更准确的说法：提示词是你和模型之间的接口契约。**

你写一个函数：

```python
def compute_fib4(age: int, ast: float, plt: float, alt: float) -> float:
    """计算 FIB-4 肝纤维化指数，返回一个浮点数。"""
```

你会写清楚参数类型、返回值类型。**提示词也是一样的东西，只是用自然语言写的。**

### 一个不合格的提示词

```
帮我分析一下这个病人的肝功
```

**问题：**

| 缺什么 | 后果 |
|---|---|
| 数据没说 | 它会反问你，或者自己编数据 |
| 输出格式没说 | 每次格式不同，代码没法处理 |
| 判断依据没说 | 它会用通用常识，不是临床标准 |

### 合格的提示词

```
你是临床辅助分析助手。

任务：根据以下检验结果，判断肝纤维化风险等级。

数据：
- 年龄：52 岁
- AST：45 U/L
- 血小板：120 ×10^9/L
- ALT：38 U/L

输出要求：
- 只输出一个 JSON 对象，不要任何解释、不要 markdown 代码块
- 字段：risk_level（高/中/低）、fib4（数值，保留两位小数）、reason（一句话）
```

**区别就在这三块：角色、数据、输出契约。**

---

## 二、四段式结构

**这是本节最实用的一条，记住这四段，覆盖 80% 的场景。**

```
【角色】你是谁，你的专业边界在哪
【任务】要你干什么，一步还是多步
【输入】数据是什么，怎么读
【输出】返回什么格式，什么算合格
```

### 逐段拆解

**① 角色：管的是「它说谎的方向」**

```
你是医学影像科的辅助诊断助手，只回答影像相关问题。
```

**为什么有用**：不限定角色时，模型会用「通用百科」的口气回答，什么都敢说。限定角色后，超出范围的它会倾向于说「这超出了我的范围」。

**注意：角色不能治幻觉。** 它只是让回答的口吻和专业范围收敛，**不代表内容一定对**。

**② 任务：动词要具体**

| 模糊 | 具体 |
|---|---|
| 分析一下 | 判断属于哪一类，并给出依据 |
| 帮我看看 | 找出所有异常项，逐条列出 |
| 处理数据 | 把单位统一成 mg/dL，输出表格 |

**③ 输入：数据用标记包起来**

```
【待分析数据】
...
【数据结束】
```

**为什么要标记**：如果数据里本身含有「忽略上面所有指令」这类文字，没有边界的话模型可能把它当指令执行。这叫 **提示词注入**。

**④ 输出：给一个真实的样例**

**这是最有效的一段。** 不要描述格式，直接给一个样例：

```
输出格式（严格按此结构）：
{"risk_level": "高", "fib4": 3.21, "reason": "年龄和AST升高、血小板降低"}
```

**给样例比描述格式有效 5 倍以上。** 因为模型是「照猫画虎」的，不是「理解规范」的。

## 三、Few-shot：给几个例子

**结构：给 2-3 个「输入 → 输出」的完整示例，再给真实输入。**

```python
prompt = """把下面的影像描述改写成结构化结论。

示例1：
输入：右肺下叶见斑片状高密度影，边界模糊
输出：{"部位": "右肺下叶", "征象": "斑片状高密度影", "边界": "模糊"}

示例2：
输入：左肺上叶见结节，直径约 8mm，边缘光滑
输出：{"部位": "左肺上叶", "征象": "结节", "边界": "光滑", "大小_mm": 8}

现在处理：
输入：双肺见弥漫性磨玻璃影，以胸膜下分布为主
输出："""
```

**几个经验值：**

| 项 | 建议 |
|---|---|
| 例子数量 | 2-3 个最好，超过 5 个边际收益很低且白烧 token |
| 例子顺序 | 最后一个例子和真实输入越像越好（模型有近因偏好） |
| 例子质量 | **一个坏例子比没有例子更糟**，它会污染输出 |

## 四、思维链（Chain of Thought）

**让模型先写推理过程，再给结论。**

```
请先一步步分析，最后再给结论。
```

**为什么有的任务有效**：模型每多生成一个 token，就多一次「用上下文计算」的机会。推理步骤写出来，后面的结论是在更多信息上算的。

### 什么时候用，什么时候不用

| 场景 | 用不用 CoT |
|---|---|
| 数学计算、多步推理 | **用** |
| 需要解释依据的医学判断 | **用** |
| 简单分类、提取字段 | **不用**，白花钱还拖慢 |
| 要求严格 JSON 输出 | **小心**，推理文字会污染 JSON |

### 和推理模型的区别

你用的 `deepseek-flash` 是**推理模型**——它自带 `thinking` 块，你什么都不用写，它自己会想。

```
返回里已经有 [thinking] 了，不需要你在提示词里再要求它「一步步想」
```

**但自己写 CoT 仍然有用**，因为 `thinking` 你看不到、也控制不了，而写在正文里的推理你能读到。

## 五、结构化输出：最容易出问题的地方

### 先说结论：`json.loads()` 一定会崩

**新手最常见的写法：**

```python
answer = "".join(b["text"] for b in d["content"] if b["type"] == "text")
data = json.loads(answer)          # ← 这里会炸
```

**为什么炸：** 模型经常这么回：

```
好的，我为你分析如下：
```json
{"risk_level": "高", "fib4": 3.21}
```
希望这个分析对你有帮助。
```

**它不是 JSON，是「包含 JSON 的一段话」。**

### 四种典型破坏方式

| 破坏方式 | 长什么样 |
|---|---|
| 包了 markdown 代码块 | ` ```json ... ``` ` |
| 前后有客套话 | 「好的，以下是结果：」 |
| 字段缺失或改名 | 你要 `risk_level`，它给 `risk` |
| 类型不对 | 你要数字，它给字符串 `"3.21"` |

### 三层防御，缺一不可

**第一层：提示词约束**

```
只输出 JSON，不要任何解释文字，不要 markdown 代码块。
```

**第二层：容错解析**

```python
import json, re

def parse_json(text):
    """尽量从模型输出里抠出 JSON，失败返回 None"""
    text = text.strip()

    # 1. 去掉 markdown 代码块
    fence = "`" * 3                      # 不直接写三个反引号，否则会破坏本文档的代码块
    text = re.sub("^" + fence + r"(?:json)?\s*", "", text)
    text = re.sub(r"\s*" + fence + "$", "", text)

    # 2. 直接试
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass

    # 3. 找第一个 { 到最后一个 } 之间的内容
    start, end = text.find("{"), text.rfind("}")
    if start != -1 and end > start:
        try:
            return json.loads(text[start:end+1])
        except json.JSONDecodeError:
            pass

    return None
```

**第三层：字段校验**

```python
def validate(data, required=("risk_level", "fib4", "reason")):
    if data is None:
        return False, "解析失败"
    missing = [k for k in required if k not in data]
    if missing:
        return False, f"缺字段: {missing}"
    if not isinstance(data["fib4"], (int, float)):
        return False, f"fib4 类型错误: {type(data['fib4'])}"
    return True, "ok"
```

### 都失败了怎么办

```python
data = parse_json(answer)
ok, msg = validate(data)
if not ok:
    # 重试一次，把错误告诉模型
    retry_prompt = f"你的输出无法解析：{msg}\n请只输出纯 JSON，不要任何其他文字。"
    # ... 重新请求
```

**这叫「带反馈的重试」。** 实测能把成功率从 70% 提到 95% 以上。

## 六、医学场景的三条额外要求

**这三条你在其他教程里看不到，但对你的方向是硬要求。**

### ① 强制 temperature = 0

```python
json={"model": "deepseek-flash", "temperature": 0, ...}
```

**理由**：同一个病人、同一份数据，今天分析出一个结论，明天分析出另一个——这在临床上不可接受。

### ② 要求给出依据，并要求它说「不确定」

```
如果信息不足以判断，risk_level 填 "不确定"，并在 reason 里说明缺什么。
```

**为什么有效**：模型的默认行为是「必须选一个」。你明确给它一个「不确定」的出口，它才会用。

**这不是消除幻觉，是让它把不确定的部分标出来。**

### ③ 关键数值不要让模型算

```
错误做法：把年龄、AST、血小板丢给它，让它算 FIB-4
正确做法：你的代码算好 FIB-4，把结果作为输入给它，让它只做解释
```

**为什么**：大模型的算术是不可靠的，尤其是多步计算和小数。**能用代码算的，一律用代码算。**

| 版本 | 内容 |

| B | 四段式 |

**结论写一句话：哪一段贡献最大？**

### 练习 16-2-B（必做）：构造提示词注入

```

## 十一、常见错误

| 错误 | 表现 | 改法 |
|---|---|---|
| 直接 `json.loads` | `JSONDecodeError` | 先 strip 代码块，再找括号 |
| 只写「输出 JSON」 | 它包了 markdown | 明确写「不要代码块」 |
| 例子给太多 | 花费翻倍，效果不增 | 2-3 个够 |
| 用 `temperature=0.7` | 同一输入结果不稳定 | 改 0 |
| 让模型算数 | 偶尔算错，且错得很自然 | 用代码算，模型只解释 |
| 没给「不确定」出口 | 信息不足也硬给结论 | 明确允许输出「不确定」 |
| 数据不包边界 | 被提示词注入 | 用标记包起来 |

你现在能让模型**稳定地按格式说话**了。
