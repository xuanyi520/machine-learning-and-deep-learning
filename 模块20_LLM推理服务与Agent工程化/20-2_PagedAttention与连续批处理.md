## 一、先算清显存账

**一个推理服务，显存被三样东西占着：**

```
总显存 = 模型权重 + KV Cache + 激活值/临时缓冲
```

### 以 qwen2.5:7b Q4 为例

**模型权重：**

```
7B 参数 × 0.5 字节（4bit）= 约 3.5 GB
实测 Ollama 显示 4.4 GB（含量化元数据）
```

**KV Cache（用 19-1 的公式）：**

```python
def kv_cache_gb(seq_len, n_layers, n_kv_heads, head_dim, batch=1, bytes_per=2):
    return seq_len * n_layers * n_kv_heads * head_dim * 2 * batch * bytes_per / 1024**3

# 假设 7B 模型：28 层、4 个 KV 头、头维度 128、fp16
for n in [1024, 4096, 8192]:
    for b in [1, 4]:
        print(f"  序列 {n:5d}, batch {b}: {kv_cache_gb(n, 28, 4, 128, b):.2f} GB")
```

**算出来大概是这样：**

| 序列长度 | batch=1 | batch=4 |
|---|---|---|
| 1024 | 0.07 GB | 0.27 GB |
| 4096 | 0.27 GB | 1.09 GB |
| 8192 | **0.55 GB** | **2.19 GB** |

**结论：8 GB 显存里，模型占 4.4 GB，剩下 3.6 GB 给 KV Cache。**

**所以：**

```
单请求 8K 上下文 → 0.55 GB，能同时跑 6 个左右
4 个请求各 8K     → 2.19 GB，快撑满了
```

**这就是为什么「并发数」不是随便设的——它直接由显存和上下文长度决定。**

## 二、朴素做法的浪费：内部碎片

**假设你要服务 4 个用户，每个最多可能要 8192 token。**

### 朴素做法：按最大值预分配

```
用户 A：需要 500 token  → 分配 8192 的空间
用户 B：需要 3000 token → 分配 8192 的空间
用户 C：需要 200 token  → 分配 8192 的空间
用户 D：需要 6000 token → 分配 8192 的空间

实际用到：500+3000+200+6000 = 9700
实际分配：8192 × 4 = 32768

浪费：23068 / 32768 = 70%
```

**这就是「内部碎片」——分配了但没用上的空间。**

**后果：**

**本该能服务 10 个用户的显存，只服务了 4 个。**

### PagedAttention 的做法

**把 KV Cache 切成固定大小的页（通常 16 个 token 一页），按需分配。**

```
用户 A：500 token → 分 32 页（512 位置）
用户 B：3000 token → 分 188 页
用户 C：200 token → 分 13 页
用户 D：6000 token → 分 375 页

实际分配：608 页 × 16 = 9728 位置
实际用到：9700

浪费：28 / 9728 = 0.3%
```

**效果：显存利用率从 30% 提到 99%。**

### 一个容易混淆的点：页表

**分页之后，KV Cache 在物理显存上不连续了。**

**所以要有一张「逻辑位置 → 物理页」的映射表，注意力计算时按表去找。**

**这和操作系统的虚拟内存管理完全一样。**

**代价：多了一次间接寻址。但相比显存利用率的提升，这个开销很小。**

## 三、连续批处理：真正的吞吐来源

### 传统批处理的问题

**假设三个请求同时到：**

```
请求 A：要生成 500 token
请求 B：要生成 50 token
请求 C：要生成 100 token
```

**传统批处理的做法：**

```
第 1 步：[A, B, C] 一起跑
...
第 50 步：[A, B已完成, C] → B 的位置空着，GPU 在浪费
第 100 步：[A, C已完成] → 两个位置空着
第 500 步：[A] → 三个位置空着
```

**整个过程中，GPU 有一大半时间在做「等待最慢的那个人」。**

### 连续批处理的做法

```
第 1 步：[A, B, C]
...
第 50 步：B 完成 → 立刻把新来的 D 塞进去 → [A, C, D]
第 100 步：C 完成 → 新的 E 进来 → [A, D, E]
第 500 步：A 完成
```

**GPU 始终保持满载。**

### 为什么这样能快

**生成一个 token，需要把整个模型的权重从显存读一遍。**

```
单请求： 读 4.4 GB 权重 → 算 1 个 token → 再读 4.4 GB → 算下一个
批处理： 读 4.4 GB 权重 → 算 4 个 token（每个请求一个）← 同样的读取量
```

**关键：权重读取的成本被 4 个请求分摊了。**

**这就是为什么批处理能提升吞吐——不是算得更快，是「同样的显存读取干了更多的活」。**

## 四、但实测发现：短请求时并发反而更慢

**这是本机跑出来的结果，和教科书说的不完全一致。**

### 场景一：短请求（每个只生成约 22 token）

```
串行 4 次：总耗时 1.75s，吞吐 50.4 tok/s
并发 4 个：总耗时 2.07s，吞吐 42.5 tok/s

吞吐提升: 0.84x      ← 变慢了
墙钟时间: 多花 19%
```

### 场景二：长请求（每个生成 300 token）

```
并发 1：墙钟 6.91s，生成 300 tokens，吞吐 43.4 tok/s
并发 2：墙钟 10.44s，生成 600 tokens，吞吐 57.5 tok/s   ← +32%
并发 4：墙钟 19.23s，生成 1200 tokens，吞吐 62.4 tok/s  ← +44%
```

### 怎么解释这个差异

**短请求的瓶颈不在 GPU，在「请求调度」：**

```
每个请求要经历：建立连接 → 加载 prompt → 调度 → 生成 22 个 token → 收尾
                                  ↑
                        这段开销比 22 个 token 的计算还大
```

**批处理省的是「权重读取」，但短请求时这部分占比很小，反而是调度开销占了大头。**

**并发之后：**

```
4 个请求抢同一块 GPU → 每个的 TTFT 都变长
总时间没减少，反而多了上下文切换的开销
```

**长请求则不同：**

```
生成 300 个 token，权重读取占绝对大头
批处理把这部分摊薄了 → 吞吐明显提升
```

### 三条实用结论

| 你的场景 | 并发有用吗 |
|---|---|
| Agent 每次只调一次短回答 | ❌ 用处不大，甚至更慢 |
| 批量生成报告、长文档摘要 | ✅ 明显有效 |
| 大量短请求（如分类标注） | ⚠️ 不如做批量预处理 |
| 用户交互式对话 | ✅ 有意义（多个用户同时在用） |

**面试时能说出「并发不是万能的，取决于请求长度和瓶颈在哪」，比背「批处理提升吞吐」强得多。**

## 五、并发数的上限怎么定

**不是越多越好。三个约束：**

### 约束一：显存

```
可用 KV Cache 空间 = 总显存 - 模型权重 - 系统开销
最大并发 ≈ 可用空间 / (单请求 KV Cache × 上下文长度)
```

**实测你的机器：**

```
8 GB - 4.4 GB(模型) - 0.5 GB(系统) = 3.1 GB 可用
单请求 4K 上下文 ≈ 0.27 GB
最大并发 ≈ 11 个
```

**但这是理论值，实际要留余量，建议按 60-70% 算，即 7 个左右。**

### 约束二：GPU 计算

**并发数增加，每个请求的生成速度会下降。**

**实测（长请求）：**

```
并发 1：单个请求 43.4 tok/s
并发 4：总 62.4 tok/s，平均每个 15.6 tok/s
```

**单个用户感受到的速度降到了原来的 36%。**

**这就是 trade-off：吞吐上去了，但每个人的体验变差了。**

### 约束三：你的业务能不能接受

| 业务 | 能接受单请求降速吗 |
|---|---|
| 后台批量处理 | ✅ 能，只看总时长 |
| 交互式对话 | ⚠️ 适可而止，降到一半就难受了 |
| 实时诊断 | ❌ 不能，宁可排队 |

**用第一节的公式，算你机器上不同配置的并发上限：**

```python
def max_concurrent(total_gb, model_gb, reserve_gb, seq_len,
                   n_layers=28, n_kv_heads=4, head_dim=128):
    avail = total_gb - model_gb - reserve_gb
```

## 十、常见错误

| 错误 | 现象 | 改法 |
|---|---|---|
| 以为并发越多越好 | 变慢、OOM | 实测找甜点 |
| 按最大长度预分配 KV Cache | 利用率只有 30% | 分页 |
| 忽略上下文长度对并发的影响 | 估算严重偏离 | 用公式算 |
| 只看吞吐不看单请求速度 | 用户体验崩了 | 两个都要看 |
| 短请求也上高并发 | 得不偿失 | 短请求走串行或批量预处理 |

**你知道了怎么把模型跑得快、跑得稳。**
