# 20-3 上下文工程

**建议用时：8 小时**

**出口标准：能算出一次 Agent 调用的 token 预算，能设计一套压缩和排序策略，并能说出为什么上下文不是越长越好。**

## 〇、这一节在解决什么

**2026 年的 Agent 岗位 JD 里，有一个词出现的频率在快速上升：**

> **「对上下文工程（Context Engineering）、工具调用、Skill 设计有深入理解」**

**这不是「提示词工程」换个说法。它是更大的一个概念。**

**这一节要讲清：**

```
① 上下文工程和提示词工程差在哪
② 一次 Agent 调用的上下文由哪几部分组成
③ 怎么分配 token 预算
④ 上下文太长时怎么压缩
⑤ 顺序为什么也重要
```

---

## 一、两个词的区别

| | 提示词工程（16-2 学的） | 上下文工程（这一节） |
|---|---|---|
| 管什么 | **你写的那段话怎么说** | **模型这次能看到的所有东西** |
| 范围 | 一个 prompt | 系统提示 + 工具定义 + 历史 + 检索结果 + 记忆 |
| 类比 | 写一封信 | **设计整个办公桌的摆放** |
| 什么时候重要 | 单次调用 | **多轮 Agent、长会话** |

**一句话：**

> **提示词工程解决「怎么说」，上下文工程解决「给它看什么」。**

**为什么后者在 Agent 时代变得更重要：**

```
普通对话：一次调用，一个 prompt → 提示词工程够了
Agent：  一次任务，10+ 次调用，每次的上下文都在变
         → 必须系统化管理「每次塞什么进去」
```

---

## 二、一次 Agent 调用的上下文，由五部分组成

**拿你的医学影像 AI 助手举例：**

```
┌──────────────────────────────────────────┐
│ ① 系统提示      "你是医学影像助手……"      │  约 300 token
├──────────────────────────────────────────┤
│ ② 工具定义      三个工具的 JSON Schema     │  约 800 token
├──────────────────────────────────────────┤
│ ③ 对话历史      用户问的 + 模型的回答      │  增长最快
├──────────────────────────────────────────┤
│ ④ 检索结果      从知识库检索到的指南片段    │  约 2000 token
├──────────────────────────────────────────┤
│ ⑤ 工作记忆      已确认的事实、已调用的工具  │  约 200 token
└──────────────────────────────────────────┘
```

### 各部分的特点

| 部分 | 大小 | 变化频率 | 能压缩吗 |
|---|---|---|---|
| ① 系统提示 | 固定 | 从不 | 能不压就不压 |
| ② 工具定义 | 固定 | 很少 | 工具多时才考虑 |
| ③ 对话历史 | **增长最快** | 每轮都变 | **必须压** |
| ④ 检索结果 | 大 | 每次不同 | **可以截断** |
| ⑤ 工作记忆 | 小 | 每轮更新 | 不压 |

**注意 ③ 和 ④：它们是 90% 的 token 消耗来源，也是唯一值得优化的地方。**

**系统提示和工具定义是固定的，压缩它们会伤筋动骨。**

## 三、算一次调用的 token 预算

**这是上下文工程的第一步：先知道钱花在哪。**

```python
def estimate_tokens(text: str) -> int:
    """中文约 1 字 = 1.3 token，英文约 1 词 = 1.3 token
    粗略估算：中文字符数 × 1.5 + 英文单词数 × 1.3
    """
    zh = sum(1 for c in text if '一' <= c <= '鿿')
    en = len([w for w in text.split() if w.isascii()])
    return int(zh * 1.5 + en * 1.3)


def budget_breakdown(system, tools, history, retrieved, memory):
    parts = {
        "系统提示": estimate_tokens(system),
        "工具定义": estimate_tokens(tools),
        "对话历史": estimate_tokens(history),
        "检索结果": estimate_tokens(retrieved),
        "工作记忆": estimate_tokens(memory),
    }
    total = sum(parts.values())
    print(f"{'部分':12s} {'token':>8s} {'占比':>8s}")
    print("-" * 32)
    for k, v in parts.items():
        print(f"{k:12s} {v:8d} {v/total*100:7.1f}%")
    print("-" * 32)
    print(f"{'合计':12s} {total:8d}")
    return parts
```

**跑一下典型的 Agent 调用：**

```python
budget_breakdown(
    system="你是医学影像助手，根据影像和指南回答问题。（约 300 字）",
    tools="三个工具的 JSON Schema 定义（约 500 个英文字符）",
    history="用户：这张CT有肺炎吗？\n助手：根据模型预测……（约 800 字）",
    retrieved="从指南里检索到的三段内容（约 1500 字）",
    memory="- 已确认：AFP 45\n- 已调用：predict_image",
)
```

**你会看到「检索结果」和「对话历史」占了大头。**

### 一个真实的比例

**一个跑了 5 轮的医学 Agent，典型分布：**

```
系统提示    300   (3%)
工具定义    800   (8%)
对话历史   4000  (40%)   ← 最大
检索结果   4500  (45%)   ← 最大
工作记忆    400   (4%)
────────────────────
合计      10000
```

**所以优化的重点很明确：对话历史和检索结果。**

## 四、五种压缩策略

### 策略一：截断检索结果（最简单）

```python
def truncate_chunks(chunks, max_chars=2000):
    """保留总字符数不超过 max_chars，从最相关的开始保留"""
    out, total = [], 0
    for c in chunks:                # 假设已按相关度排序
        if total + len(c) > max_chars:
            break
        out.append(c)
        total += len(c)
    return out
```

**注意：按相关度排序后再截断，不要按原文顺序截。**

**按原文顺序截，可能把最相关的第三段丢掉，留下不怎么相关的前两段。**

### 策略二：历史摘要（压缩对话历史）

**多轮对话越来越长，但早期的细节往往不再需要。**

```python
def summarize_history(messages, keep_recent=4):
    """保留最近 N 条，更早的压缩成摘要"""
    if len(messages) <= keep_recent:
        return messages

    old = messages[:-keep_recent]
    recent = messages[-keep_recent:]

    # 用本地小模型做摘要（零成本）
    summary_prompt = f"""把下面的对话压缩成 3 行以内的要点，只保留事实：

{chr(10).join(m['content'][:200] for m in old)}

要点："""
    summary = call_local_model(summary_prompt)

    return [{"role": "system", "content": f"【之前的对话要点】\n{summary}"}] + recent
```

**关键：摘要要保留「事实」，不保留「对话的客套」。**

### 策略三：工作记忆代替历史（最有效）

**16-5 讲过工作记忆，这里要说清它为什么能省 token。**

**对比两种做法：**

```
做法 A（保留原始历史）：
  用户：查一下 AFP
  工具：{"afp": 45, "unit": "ng/mL", "reference": "<7"}
  （这轮占 50 token）

  三轮之后，这条还在历史里
  → 每轮都要重发这 50 token
  → 5 轮就是 250 token

做法 B（抽成工作记忆）：
  工作记忆里只有：AFP = 45 ng/mL（参考上限 7）
  （占 15 token）

  → 每轮只发 15 token
  → 5 轮是 75 token
```

**而且工作记忆更准确——原始的工具返回里可能有一堆没用的字段。**

### 策略四：按需检索（不要一次全给）

**错误做法：把检索到的 10 段全塞进去。**

**正确做法：先给 2-3 段，模型说不够再补。**

```
第 1 次：检索 top-3，给模型
  → 模型："资料不足以回答 III 期的治疗"
第 2 次：改用新关键词检索，再给 top-3
```

**这叫「迭代检索」，是 RAG 的进阶做法。**

**代价是多一次调用，但省下的 token 通常值得。**

### 策略五：工具定义瘦身

**工具多的时候（比如 20 个），光定义就占几千 token。**

**三种做法：**

| 做法 | 效果 |
|---|---|
| **分组**：只给当前任务相关的工具 | 省 70% |
| **精简 description** | 省 30% |
| **工具检索**：根据问题先选工具，再给定义 | 省 80%，但多一步 |

**MCP 的一个价值就在这：工具可以按需加载，不用一次全塞进去。**

## 五、顺序：模型对上下文位置的敏感

**同样内容，放的位置不同，效果可能差很多。**

### 三个实证发现

**① 开头和结尾权重高（"中间迷失"现象）**

**长文本里，模型对中间部分的记忆最弱。**

```
[开头]   ← 记得牢
[中间]   ← 容易忽略
[结尾]   ← 记得牢
```

**所以关键信息不要放在正中间。**

**② 最近的对话权重最高**

**对话历史里，越靠后的越重要。**

**所以最新的一轮必须完整保留，早期的可以压缩。**

**③ 指令放最后，比放开头更有效**

**实验发现：把「必须输出 JSON」这类硬约束放在用户问题后面，比放在系统提示里遵守率更高。**

```python
messages = [
    {"role": "system", "content": "你是医学影像助手。"},
    {"role": "user", "content": f"{检索结果}\n\n问题：{question}\n\n"
                                 f"请只输出 JSON，不要其他文字。"},
]
```

**但这不是绝对的，不同模型表现不同。**

## 六、Agent 里的上下文生命周期

**这是上下文工程在 Agent 场景的特殊之处：上下文不是一次性的，是循环增长的。**

```
第 1 轮：系统(300) + 工具(800) + 问题(50) + 检索(2000) = 3150
第 2 轮：上一轮的全部(3150) + 新工具结果(200) = 3350
第 3 轮：3350 + 新检索(2000) = 5350
第 5 轮：可能到 10000+
```

### 三个必须设的阈值

```python
CONFIG = {
    "max_context_tokens": 12000,      # 超过就触发压缩
    "keep_recent_turns": 4,           # 保留最近几轮原文
    "max_retrieval_tokens": 2500,     # 检索结果上限
}
```

### 触发压缩的时机

```python
def check_and_compress(messages, total_tokens):
    if total_tokens > CONFIG["max_context_tokens"]:
        messages = summarize_history(messages, CONFIG["keep_recent_turns"])
        print(f"上下文超过阈值，已压缩")
    return messages
```

### 一个真实的教训

**你在用 Claude Code 时踩过这个坑：**

**上下文涨到 21 万 token 后，压缩请求算出负数 max_tokens，压缩失败，之后每条消息都拖着全部历史。**

**这个问题的本质就是：没有及时压缩，上下文失控。**

**所以这一节的规则不是理论——是必须实现的工程约束。**

## 十一、常见错误

| 错误 | 现象 | 改法 |
|---|---|---|
| 把检索结果全塞进去 | 贵、慢、抓不住重点 | 按相关度截断 |
| 不压缩历史 | 几轮后上下文爆炸 | 设阈值触发摘要 |
| 摘要压掉关键数字 | Agent 失忆 | 只压缩对话，不压事实 |
| 按原文顺序截断 | 丢掉最相关的 | 先排序再截 |
| 关键指令放中间 | 遵守率低 | 放最后或最前 |
| 不测压缩后的效果 | 以为省钱了其实变笨 | 必须对比回答质量 |
